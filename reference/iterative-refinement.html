Iterative refinement

Five moves from guide §3.5. Find the one whose symptom matches the stem.

Symptom → move

read inconsistently
The prose instruction exists, but output varies between runs → 2–3 concrete input→output examples, placed where the readings split. L13
edge case wrong
One kind of input fails (e.g. a null in a migration) → send that input, its expected output, and its actual output. Not "be careful with X". L13
keeps regressing
Fixes keep breaking cases that worked before, and the expected outputs are known → write the tests first (expected behaviour, edge cases, performance), then iterate by sharing the failing tests. Beats one long prose message: the tests re-check every case on every round. L20
unfamiliar domain
Interview pattern: have Claude ask you questions (cache invalidation, failure modes) before it implements anything. Tests need known expected behaviour; the interview is for when you don't know it yet. L20
several issues
Fixes that interact → one detailed message covering all of them. Independent fixes → one at a time. Tangled if one's output feeds another, they share a step, or fixing one broke another. Tie-break: fixes keep breaking each other and expected outputs are known → tests first (row above). L18

Picking examples

where
At the forks: inputs where plausible readings give different outputs. An example every reading already gets right teaches nothing.
how many
2–3 for a transformation (guide §3.5); 2–4 for ambiguous judgement calls (guide §4.2).
shape
Relevant, diverse, wrapped in <example> tags (prompting docs).

When examples are the distractor

info missing
Minimal tool descriptions → expand the descriptions, not the examples (guide sample Q2; objective 2.1).
must never
A hard rule needs a code gate. Examples change the odds; they don't guarantee anything (L5).
"more detail"
Rewriting the instruction at greater length is the prose that already failed, only longer.
