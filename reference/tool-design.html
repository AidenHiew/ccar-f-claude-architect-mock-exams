Tool design and tool_choice

The model sees name + description + schema, in one prompt with your system prompt. Nothing else.

Description checklist (2.1)

does
What it does and what it returns
input
Format of each parameter, with an example; unambiguous names (user_id, not user)
when
When to use it, and when not to
sibling
"Use X instead when…" for every similar tool
limits
What it does not return; edge cases

Misrouting: diagnose by where errors cluster

spread evenly
Thin descriptions → expand (checklist)
between 2 tools
Overlap → rename + rewrite to distinct purposes; prefix by service (jira_search)
wrong output shape
Generic tool, several jobs → split into purpose-specific tools with I/O contracts
on one phrase
Descriptions already good → system prompt keyword line; reword it

Consolidate (one tool, action param) when only the verb changes on one resource. Split when the jobs need different outputs. On the exam, the guide's split pattern wins.

Tool distribution (2.3)

scope
4–5 role tools per agent, not 18
cross-role
Narrow tool for the frequent case (verify_fact); complex cases via coordinator
constrain
Generic → validated (fetch_url → load_document)

tool_choice (set per request)

auto
Tool or text. Default with tools
any
Must call a tool; model picks which. No text before the call (prefill)
tool
Must call that tool. No text before the call (prefill)
none
No tool calls. Default without tools

Sequencing

Request 1: force the prerequisite. Requests 2+: auto, so the model can call dependent tools on real data. Forcing every turn means the dependent tools are never called. any every turn does not control order.

Current-docs delta (not on exam v0.2)

Opus 5.5 · Sonnet 5.5 · Fable 5.1 · Mythos 5.1: any/tool → 400. Use auto + strict tool use, or structured outputs.
