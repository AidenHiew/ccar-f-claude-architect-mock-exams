When a retry can help

Sort each failure before you fix it. One stem can hold two failures that need two different fixes.

The one question for every failed field: is the right answer already in what the model was given?
Yes → retry, and tell it exactly what was wrong.
No → a retry cannot help. Use lesson 15's question: can the system go and get it?

An everyday example. You ask a colleague to copy details from a customer's letter onto a form. Two boxes come back wrong.

  • The date box says "3 Oct". The form wants 2026-10-03. The date is in the letter; it was just written the wrong way. Hand the form back with "dates must be YYYY-MM-DD" and it comes back right.
  • The account number box is empty. The account number isn't in the letter. It's on the bank statement in your drawer. Handing the form back ten times, however clearly you explain, gets you the same empty box. Give your colleague the statement.

Same form, two failures, two different fixes. Writing "N/A" in both boxes would hide a date you could have had and an account number the business needs.

1 · Two kinds of failure

The answer is in the documentThe answer is not in the document
Looks likeWrong format ("3 Oct", "1,204.50" as text); a value in the wrong field; line items that don't add up to what the model wroteA field that's empty every time, because its source is a different document, system or page that was never sent
Does a retry help?Yes. The model can read it again and correct itself.No. The input is the same, so the gap is the same.
FixRetry with the specific errorSend the missing source (lesson 15). Leave it empty only if it exists nowhere.

One thing you never need to retry: broken JSON. The guide says extraction through a tool with a JSON schema eliminates schema syntax errors. The errors left over are about meaning (wrong format inside a field, values that don't add up, a value in the wrong field), and those are the ones a retry fixes.

2 · What a good retry contains

A retry that only says "try again" or "be more careful" gives the model nothing new. The guide lists three things a correction request needs: the original document, the extraction that failed, and the specific validation errors.

// follow-up request after validation fails
Here is the invoice again:          [original document]
Your previous extraction was:       [the failed JSON]
It failed validation:
  - invoice_date "3 Oct" must be YYYY-MM-DD   [specific error]
  - line_items sum to 5,040 but total is 5,400
Return a corrected extraction.

Each piece does a job. The document lets the model look again. The failed output shows it what it did. The error tells it exactly what to change.

3 · Why a retry can't find what isn't there

Every retry sends the model the same document. If contract_value isn't in that document, a clearer error message doesn't add it. The model can only leave the field empty again or guess a number, and a guess is worse than empty because it looks real. That is why the guide names this as the limit of retry: information that "exists only in an external document not provided".

So when a field fails every time, and the stem tells you where the value really lives, stop retrying. Then ask lesson 15's question: can the system go and get it? Usually yes: send that document.
