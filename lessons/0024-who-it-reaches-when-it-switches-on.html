CCA Foundations · Lesson 24 · Claude Code setup and tool design

Who it reaches, and when it switches on

On the practice papers and quizzes you sat on 19 and 20 October, you lost points in four ways. Each one is shown below in full, with your pick and the correct answer, so you don't need to remember any of them.

The plain question. When you write an instruction into a file, will Claude see it in the right projects, at the right moment, and nowhere else?

An everyday example. You stick a note on your fridge at home. At the top you write "FOR TUESDAY'S PARTY ONLY". You still see the whole note every time you open the fridge, on every day of the week. The label tells you what it's for; it doesn't hide the note on other days. Now picture a different note, taped inside the door of the storeroom at work. People read it only when they walk into the storeroom, for any reason. Someone who decides at their desk to start a stock-take never sees it before they start.

Claude Code files work the same way. A file reaches the same people, in full, whatever headings are inside it. And a file tied to a folder is read only when Claude goes into that folder.

Words to start with

CLAUDE.md
A file of standing instructions that Claude reads when a session starts. ~/.claude/CLAUDE.md is your own copy, for all your projects. my-repo/CLAUDE.md is the team's copy, for one project; questions call it the root CLAUDE.md because it sits at the top of the project folder. A CLAUDE.md can also sit inside a sub-folder; then it loads only when Claude reads or edits a file in that folder.
~/ and my-repo/
~/ is your home folder on your own computer; nobody else's sessions read it. my-repo/ stands for the project's folder. Files there that are committed (saved into git, the project's shared history) reach every teammate.
At launch
The moment a Claude Code session starts, before you type anything. Some questions say "at startup"; it means the same.
Reach and trigger
Reach is who gets an instruction and in which projects; it depends on where the file is saved. Trigger is when the file switches on; it depends on what kind of file it is.
Exam guide
The official document from Anthropic that lists what the exam covers. This page quotes it in plain words so you can check the facts; you don't need to open it.

Other words are explained in the section where they first come up.

1 · A heading doesn't limit where a file loads

The question below asked for two things with different reach: one for all your repositories, one for this repo only. Words you'll meet in it:

  • CLAUDE.local.md: a CLAUDE.md for just you, in one repo. It sits in my-repo/ but is kept out of git, so teammates never get it. It loads at launch in every session in that repo, until you delete the line.
  • Skill: a saved set of instructions for one task, which loads only when someone starts that task. ~/.claude/skills/ holds your own. More on skills in the next section.
  • Monorepo: one repository that holds several projects. Docstrings: the comment at the top of a function that describes it. Airflow: a tool for running data jobs; "connection dev_local_ag" is the developer's saved login for it. You don't need to know these; they are just the setting.

Practice paper 2, 20 Oct, question 20

A developer wants 2 things from Claude: Google-style docstrings in each of the 4 repositories they work in, and, in this monorepo only, tests run against their personal Airflow connection dev_local_ag. Teammates must get neither. Where should each instruction live?

✗ Your pick: ABoth in their own ~/.claude/CLAUDE.md, under a heading per repository
✓ Correct: DDocstrings in ~/.claude/CLAUDE.md, the connection in this repo's CLAUDE.local.md
The other two options (B, C)
  • BBoth in this repo's CLAUDE.local.md, copied to the other 3 repos later
  • CDocstrings in a ~/.claude/skills/ skill, the connection in CLAUDE.local.md
Where it went wrong: the docstrings part was right. It is only for you, in all 4 repositories, in every session, which is ~/.claude/CLAUDE.md. But that file loads whole in every project you open. A heading such as ## monorepo is only a label for a human reader; it does not stop the lines under it loading in the other 3 repositories. So the personal Airflow connection would leak into those 3. The connection needs its own file whose reach is just this repo and just you: CLAUDE.local.md in the monorepo.

Remember the fridge note labelled "FOR TUESDAY'S PARTY ONLY": you still see it every day. The heading ## monorepo is that label. Claude still reads the whole of ~/.claude/CLAUDE.md in every repository you open. The exam guide says instructions in ~/.claude/CLAUDE.md apply to you, in every project. A heading doesn't change that.

The check: when the question asks for two things, work out for each one who gets it and in which projects. If the answers differ, they need two different files.

2 · When does it switch on?

Words for this section:

  • Rules file: a file in my-repo/.claude/rules/ with instructions for one topic.
  • Frontmatter: a short block of settings at the very top of a file, between two --- lines.
  • paths:: a frontmatter setting in a rules file that lists which files the rule is for. For example, a rules file that starts with
    ---
    paths: tests/fixtures/**
    ---
    loads only when Claude reads or edits a file under tests/fixtures/ (the ** is explained under Glob, just below). A rules file with no paths: loads at launch in every session.
  • ~/.claude/rules/: your own private rules files, for all your projects.
  • Glob: a file-name pattern used in paths:. * stands for any name; ** means "every file and folder below here". So tests/fixtures/** means every file under tests/fixtures/, and **/*.sql means every .sql file anywhere.
  • Skill: a SKILL.md file of instructions for one task. It loads only when the task is started: usually by a person typing its name, such as /regen-fixtures. Claude can also start it when a request clearly matches it.
  • @import: a line such as @docs/release.md inside a CLAUDE.md pulls that file's text in. It loads at launch, together with the CLAUDE.md.
  • dbt and FastAPI: tools for SQL data models and for web services; they are just the setting. Test fixtures: saved sample data that tests read. Ticket: a task card in the team's to-do tracker. A model's features: the inputs a forecasting model uses.

The next two cards, from 20 and 19 October, share one mistake. In both, the job starts when a person decides to start it. Your pick put it in a file that only switches on when Claude reads or edits a certain file. Those two don't match.

In the first one, "a .claude/rules/ file with paths set to tests/fixtures/**" means a rules file that loads only when Claude reads or edits a file under tests/fixtures/. "Loads in 40% of sessions" means it switched on in 4 of every 10 sessions, usually ones that didn't need it.

Practice paper 2, 20 Oct, question 25

A 70-line procedure for regenerating forecast test fixtures sits in a .claude/rules/ file with paths set to tests/fixtures/**. It's needed about once a month, when someone decides a model's features have changed. The rule loads in 40% of sessions because tests read fixtures, yet regenerations start from a ticket, before any fixture is opened, and Claude often lacks the procedure. Where should it live?

✗ Your pick: CA CLAUDE.md inside tests/fixtures/, loaded when Claude works there
✓ Correct: DA project skill, /regen-fixtures, committed in .claude/skills/
The other two options (A, B)
  • AThe same rule, with its paths widened to tests/** to load sooner
  • BThe root CLAUDE.md, where it loads at the start of each session
Where it went wrong: a CLAUDE.md inside tests/fixtures/ loads when Claude reads or edits a file in that folder. That is the same trigger as the paths rule that was already failing: it fires on file access. The job starts from a person's decision, before any file is opened, so a file-based trigger is either too late or fires for the wrong reason (tests read fixtures all the time). Something a person decides to start is a skill.

Lesson 21 quiz, 19 Oct, question 6

A 250-line checklist for cutting a release sits in the root CLAUDE.md. Releases happen about once a month, when someone decides to start one, and they aren't tied to editing any particular files. Where should the checklist go?

✗ Your pick: AA .claude/rules/ file with paths set to release/** for the checklist
✓ Correct: DA project skill, /cut-release, that people run to start a release
The other two options (B, C)
  • BAn @import of a release.md file from the root CLAUDE.md instead
  • CA CLAUDE.md in the release/ folder, loaded when Claude works there
Where it went wrong: the same mistake as the card just before it: a person starts the job, but the pick used a file-based trigger. A paths rule fires when Claude reads or edits a matching file. A release starts when a person decides to start one, and the question says releases aren't tied to editing any particular files. A job a person decides to start belongs in a skill.

A CLAUDE.md in a folder and a rules file with paths: look different, but they switch on the same way: when Claude reads or edits a file in the right place. Words like "when someone decides" or "starts from a ticket" point to the other trigger: a person starting it. That is what a skill is for. The exam guide describes skills as workflows you start when you need them.

The next question is the opposite case. In this one the rules were meant to load only for certain files, but none of the rules files had a paths: line.

Practice paper 2, 20 Oct, question 24

A teammate split the 600-line root CLAUDE.md into 9 topic files in .claude/rules/: dbt.md, airflow.md, fastapi.md and 6 more, none with frontmatter. Sessions that only touch the FastAPI service still load all 600 lines at startup. The dbt, Airflow and FastAPI conventions each apply to their own files only. What should change?

✗ Your pick: AMove the 9 files into ~/.claude/rules/, out of the project's own folder
✓ Correct: CAdd paths: frontmatter to the file-specific rules, such as models/**/*.sql for dbt.md
The other two options (B, D)
  • BTurn the 9 files into skills that engineers run for that kind of work
  • DMerge them back into CLAUDE.md under a clear heading for each part of the repo
Where it went wrong: a file in .claude/rules/ with no paths: line at the top loads at launch, in every session, just like CLAUDE.md. That is why splitting saved nothing. Moving the files to ~/.claude/rules/ changes who gets them (only you, so teammates lose them) but not when: still at launch. Adding paths: changes when: each file then loads only when Claude reads or edits a matching file.

The fact behind it, as the Claude Code docs put it: a rules file without paths: loads at launch, just like CLAUDE.md. A rules file with paths: loads when Claude reads or edits a matching file. The exam guide says the same from the other side: paths: is how you make a rule load only when matching files are being edited.

The check: ask "what starts this?" A session starting → CLAUDE.md, or a rules file with no paths:. Claude reading or editing certain files → a rules file with paths:, or a CLAUDE.md in that folder. A person deciding to start a job → a skill. Just for today → say it in your prompt and store nothing (for example, adding timing logs for one day only).

3 · Look at what loaded before you add anything

Words for this section:

  • /memory: a command you type in a Claude Code session. It lists the instruction files (CLAUDE.md, CLAUDE.local.md and the rest) that this session actually loaded. Some questions call these "memory files".
  • CLAUDE.local.md (explained earlier): instructions, for you only, in this one repo, in every session until you delete them.
  • Hook: a script that runs automatically just before Claude uses a tool, such as editing a file (a PreToolUse hook), or just after (a PostToolUse hook).
  • MCP server: an add-on program that gives Claude extra tools, such as access to a database. One of the optional questions below uses it.
  • Field injection: a coding style the team has banned. What it is doesn't matter here.

In this question, one person's sessions behaved differently from everyone else's.

Practice paper 2, 20 Oct, question 16

In one engineer's sessions Claude keeps using field injection, which the team's committed CLAUDE.md forbids. The other 17 engineers on the same branch don't see this, and the engineer says they have the file. A teammate suggests they copy the rule into their CLAUDE.local.md as well. What should they do first?

✗ Your pick: ACopy the rule into their CLAUDE.local.md, as the teammate suggests
✓ Correct: DRun /memory in a session of theirs to see which memory files actually load
The other two options (B, C)
  • BRewrite the rule in capitals at the top of the CLAUDE.md, with 2 examples of it
  • CAdd a PostToolUse hook that rejects any edit that adds field injection back
Where it went wrong: 17 people get the rule from the same committed CLAUDE.md (the team's shared file), so the rule itself is fine. Something about this one engineer's setup is different, and nobody knows what yet. /memory lists the memory files a session actually loaded, so it shows the cause. Copying the rule into CLAUDE.local.md (their private file for this repo) treats a cause you haven't found, and leaves a second copy that will drift. The question's word "first" asks for the check, not a fix.

The exam guide names this exact step: use the /memory command to check which instruction files are loaded when sessions behave differently from one person to the next.

You picked CLAUDE.local.md in four questions. In this one it was too early, because the cause wasn't known yet. In the other three it breaks one of its four parts. Those three are in the box below, each in full. Opening it is optional. CLAUDE.local.md has four parts:

  1. It holds instructions, not a skill or a server.
  2. It is for you only.
  3. It covers this one repo only.
  4. It applies in every session until you delete it.

In the box: the incident-summary question (full practice exam, question 19) breaks part 1, because it needed a skill. The profiling-server question (practice paper 1, question 7) breaks parts 1 and 3, because it needed an MCP server in 4 repos. The timing-logs question (practice paper 1, question 22) breaks part 4, because it was for one day only.

Optional: the other three times (full questions)

Words in these three: a spike is a short experiment you throw away afterwards. .mcp.json is the team's committed list of MCP servers. claude mcp add --scope adds a server for a chosen group: user (only you, all your projects, saved in ~/.claude.json), project (the whole team, in .mcp.json), or local, the default (only you, this project).

Full practice exam, 19 Oct, question 19

The team shares an /incident-summary skill in .claude/skills/. One engineer wants a version that writes in a terser style for their own notes, and must not change what the other 11 engineers get. They tried editing the shared SKILL.md locally, but kept nearly committing it. Where should the personal version live?

✗ Your pick: DIn CLAUDE.local.md, as an instruction to write incident summaries tersely for this engineer
✓ Correct: AIn the engineer's ~/.claude/skills/ under a different name, such as /incident-summary-terse
The other two options (B, C)
  • BIn the root CLAUDE.md, as a line asking for terse incident summaries for this engineer
  • CIn .claude/skills/ next to the team skill, with a note in its description that it is personal
Where it went wrong: CLAUDE.local.md holds instructions, not skills, and its line would change every incident summary in that repo for this engineer, including when they want the team style. A personal version of a team skill goes in ~/.claude/skills/ under a different name.

Practice paper 1, 19 Oct, question 7

One of your 14 engineers wants to try an experimental profiling MCP server that is still unstable. They want it in all 4 repositories they work in, and no teammate should see it or be asked to approve it. The warehouse repository already has a committed .mcp.json with 3 team servers. Where should the server be configured?

✗ Your pick: DIn a CLAUDE.local.md in each of the 4 repositories, as the server's launch command
✓ Correct: BAt user scope in their own ~/.claude.json, added once with claude mcp add --scope user
The other two options (A, C)
  • AIn the warehouse repo's committed .mcp.json, with its entry marked as experimental and optional
  • CWith claude mcp add run from inside the warehouse repo, leaving the scope at its default setting
Where it went wrong: CLAUDE.local.md holds instructions; Claude Code never starts an MCP server from it. It also covers one repository, not all 4. A server for only you, in all your projects, is added with --scope user and stored in ~/.claude.json.

Practice paper 1, 19 Oct, question 22

For a 1-day performance spike, a developer wants Claude to add timing logs around each database call in checkout/reserve.ts, and only in that file. They will try it in today's session only and then discard the changes, and from tomorrow they are back on normal work in that same file, where timing logs must not be added. A teammate suggests a .claude/rules/ file with paths set to checkout/reserve.ts. What is the best way to give Claude the instruction?

✗ Your pick: CAdd it to their CLAUDE.local.md, then delete the line after the spike
✓ Correct: BSay it in today's session prompt and name checkout/reserve.ts as the file
The other two options (A, D)
  • ACreate .claude/rules/spike.md with paths set to reserve.ts, left uncommitted
  • DCreate a /spike-timing skill in ~/.claude/skills/ and run it today
Where it went wrong: CLAUDE.local.md loads in every session in the repo until someone deletes the line, so tomorrow's work would get it too. Today only means nothing stored: say it in today's prompt.
The check: before you pick CLAUDE.local.md, test each of its four parts against the question. Is it an instruction (not a skill, not an MCP server)? Only you? Only this repo? Wanted in every session until removed? One "no" rules it out.

4 · Make every problem impossible, not just one

Words for this section:

  • Tool: an action an agent can call, such as "save this claim" or "run this query". A narrow tool can do only the agent's real job and nothing else.
  • PreToolUse hook: a script that runs before a tool call. It can stop that call.
  • PostToolUse hook: a script that runs after a tool call has already happened. It can only clean up or hide the result.
  • System prompt: the standing instructions given to an agent. Subagent: a second agent the main one hands work to. WHERE clause: the part of a database query that picks which rows. Claim: an insurance claim record; adjusters are the staff who review claims.

Two questions where the agent had a tool that could do far more than its job. The first question names two problems, and the hook fixes only one. The second names one requirement: the agent must be unable to reach other customers' rows. A hook that runs after the query can't give that, because the rows were already reached.

Practice paper 2, 20 Oct, question 4

The extraction agent saves its results with update_claim, a general tool that can set any field on any claim. In 1,200 runs it changed approved_payout 4 times, overwriting amounts adjusters had approved, and once edited a different claim with a similar number. Its job is to fill the 11 extraction fields on the claim it is processing. The adjusters want it unable to change anything else, not just warned. What is the best fix?

✗ Your pick: AAdd a PreToolUse hook that blocks any update_claim call whose input sets approved_payout
✓ Correct: BReplace update_claim with save_extraction, which takes only the 11 fields for the current claim
The other two options (C, D)
  • CAdd a PostToolUse hook that reverts changes to approved_payout and alerts the adjuster
  • DAdd a system prompt rule that only adjusters set payouts, with 2 examples of correct saves
Where it went wrong: the question names two problems: it changed the payout field, and it edited the wrong claim. The hook blocks the payout field only. update_claim can still change any other field and any other claim. Replacing it with save_extraction, which accepts only the 11 extraction fields for the current claim, makes both problems impossible at once.

Practice paper 1, 19 Oct, question 6

To read account data, the support agent was given run_sql, a generic tool that runs any read-only query against the customer database. In an audit of 900 chats, 7 queries returned rows for other customers, and 2 of those details were read out to the wrong person. The agent needs only the current customer's account, plan and last 10 bills, and the security team wants it unable to reach other customers' rows, not just to hide them. What is the best fix?

✗ Your pick: BAdd a PostToolUse hook that drops returned rows whose customer ID doesn't match the session's
✓ Correct: CReplace run_sql with get_my_account, which takes no customer ID and returns only the session customer's data
The other two options (A, D)
  • AAdd a system prompt rule that run_sql queries must filter on the customer ID taken from the session
  • DRoute each run_sql query through a reviewer subagent that checks the WHERE clause before it runs
Where it went wrong: the hook runs after the query, so the agent has already reached other customers' rows; the hook only hides them. The question asked for "unable to reach". A narrow tool, get_my_account, takes no customer ID at all, so there is nothing to reach.

A hook is written for one kind of call, so it covers the one problem you had in mind. A narrow tool can only do the agent's actual job, so everything else becomes impossible, including problems nobody has listed yet. The exam guide lists two ways to do this: replace a general tool with a narrow one (its example: replace a tool that fetches any web address with one that only loads valid documents), and give each agent only the tools its role needs.

The check: before reading the options, write down each problem the question names, one per line. Then cross out every option that leaves one of them still possible. A hook that blocks one thing, or cleans up afterwards, usually leaves something possible.

The four checks, in one place:
1. A file loads whole. A heading inside it does not limit where it loads.
2. Match the trigger to what starts the job. Claude reading or editing a file → a rules file with paths: or a folder CLAUDE.md. A person deciding to start a job → a skill. A rules file without paths: loads at launch, like CLAUDE.md.
3. When one person's sessions behave differently, run /memory before adding any file.
4. When the question names two problems, or says the agent must be unable to do something, the fix must make every problem impossible. A narrow tool usually does; a hook usually blocks one thing or cleans up after it.
