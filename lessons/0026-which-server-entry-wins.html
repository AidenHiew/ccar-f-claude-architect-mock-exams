Which server entry wins?

On D2/D3 Paper 4 (your fourth practice paper on Domains 2 and 3, sat on 21 October) you lost four questions: all three on setting up MCP servers (questions 9, 10 and 11) and one on CLAUDE.md (question 15). Each one is shown below in full, in teaching order rather than paper order, with your pick and the correct answer, so you don't need to remember any of them.

The plain question. When you add a tool server to Claude Code, who gets it, in which projects, and which copy is used when two have the same name?

An everyday example. You work in an office. On the kitchen wall there is a shared phone list that everyone in the office uses. Your phone has your own contacts, which go with you to every office you visit. And on your desk in this office there's a sticky note with a few numbers that only you use, only here. Say "IT help" is on all three, with three different numbers. You ring the sticky note number: it's the most specific to you and to this office. If there's no sticky note, you use the wall list. Your phone's contact is the last resort.

Claude Code keeps tool servers in the same three places, and picks between same-named ones in the same order.

The one idea: where you add a server decides who gets it and in which projects. When two places have a server with the same name, the one closest to you and this project wins: local, then project, then user.

Words to start with

CLAUDE.md and CLAUDE.local.md
Text files of standing instructions that Claude reads, such as "store prices in pence". A project can have a CLAUDE.md at the top of its folder and more inside sub-folders; when Claude works in a sub-folder, it reads all the files from the top down to that folder. Being read later doesn't make a file win; they all apply at once. CLAUDE.local.md is the same kind of file for just you, in one project, kept out of git (the project's shared history, which every teammate gets). Both hold instructions for Claude; neither sets up a server.
MCP server
An add-on program that gives Claude extra tools, such as reading a database or a ticket tracker. Each server has a name (like shop-db) and an entry: the settings that say how to reach it.
claude mcp add
The command you type in your terminal to add a server. For example, claude mcp add lint -- node tools/lint-server.js adds a server named lint that Claude Code starts by running node tools/lint-server.js. The -- separates Claude Code's own settings (before it) from the command that starts the server (after it).
Flag
An extra setting typed after a command, starting with --. --scope user is the flag --scope with the value user.
Scope
Which group a server is set up for. There are three: local, project and user. The table in section 1 explains each.
~/, committed
~/ is your home folder on your own computer; nobody else's sessions read it. A committed file is saved into git, the project's shared history, so every teammate gets it.
Session
One run of Claude Code: you start it by typing claude in your terminal, and it lasts until you close it. Commands starting with /, such as /mcp, are typed inside a session.
Environment variable
A named value set on one person's computer, outside any project file, such as CATALOG_URL=http://localhost:4000. Each person can set a different value, or none.
stdio and http
Two ways Claude Code can reach a server. A stdio server is a program on your machine that Claude Code starts with a command. An http server is already running somewhere and is reached at a web address (a url). You choose with the --transport flag, for example --transport http. The docs' basic form for a server started with a command, claude mcp add name -- command, leaves it out.

Other words are explained in the section where they first come up.

1 · Three scopes: who gets the server

This table is the whole of section 1. The scope you pick decides two things: who gets the server, and in which projects.

ScopeHow you add itSaved inWho gets itWhich projects
local (the default)claude mcp add with no --scope (or --scope local)~/.claude.json, filed under this project's folderOnly youThis project only
project--scope project.mcp.json at the top of the project folder, committedThe whole team (each person approves it once; see section 4)This project only
user--scope user~/.claude.jsonOnly youAll your projects

Two things people mix up. First, local and user are saved in the same file, ~/.claude.json. The difference is that a local server is filed under one project's folder, so it appears only there. Second, local is the default: if you leave out --scope, you get "only me, only this project".

In the question below, an engineer wanted a server for only themselves, in only this repository. That is local, and you picked user. One thing to know first: the command the engineer ran wrote the server into .mcp.json, which is the team's shared, committed file, so every teammate would get it.

D2/D3 Paper 4, 21 Oct, question 11

An engineer has written a lint MCP server that runs on their machine with node tools/lint-server.js. They want it in this repository's sessions only, and the 7 teammates on their squad shouldn't see it. They ran claude mcp add --scope project --transport http lint node tools/lint-server.js. The server failed to connect, and the command also added an entry to .mcp.json. Which command should they have run?

✗ Your pick: Bclaude mcp add --scope user lint -- node tools/lint-server.js
✓ Correct: Aclaude mcp add lint -- node tools/lint-server.js
The other two options (C, D)
  • Cclaude mcp add --scope project lint -- node tools/lint-server.js
  • Dclaude mcp add --transport http lint http://localhost:3000
Where it went wrong:
  • Your pick, --scope user, means "only you, in every project you open". The question said this repository only.
  • Leaving --scope out gives local scope: only you, only this project. That is exactly what was asked.
  • The engineer's first command was wrong in two ways. --scope project wrote the server into the shared .mcp.json, so the 7 teammates would get it. And --transport http tells Claude Code to find the server at a web address, but this server is a program started with a command (node tools/lint-server.js).
  • The correct command also puts -- before that command. It marks where Claude Code's own settings end and the command that starts the server begins.
The check: answer two questions from the stem. Who gets it: just me, or the team? Which projects: this one, or all of mine? Just me + this one = local (no flag). Team + this one = project. Just me + all of mine = user.

2 · Same name in two scopes: which one wins

A team's .mcp.json can define a server, and you can add your own server with the same name at local or user scope. Claude Code then connects to that name once, using the first entry it finds when it checks in this order:

  1. Local: only you, only this project. Checked first, so it wins.
  2. Project: the team's .mcp.json.
  3. User: only you, all your projects. Loses to both.

Like the sticky note, the wall list and your phone: the most specific one wins. Two more facts from the Claude Code docs. The whole entry from the winning scope is used; settings are not mixed from two scopes. And claude mcp list shows a warning when the same name is set up in more than one scope with different urls or commands.

In the question below, an engineer wanted their own database instead of the team's, for themselves, in this repository only. You picked a line in CLAUDE.local.md (instructions for just you, in one project).

D2/D3 Paper 4, 21 Oct, question 9

The project's committed .mcp.json defines a server named shop-db that points at the shared staging database. One engineer wants their sessions in this repository to use their own local database instead, without changing the committed file or anyone else's setup. Their 2 other projects should be unaffected. What should they do?

✗ Your pick: CAdd a line to CLAUDE.local.md telling Claude to use their database
✓ Correct: DAdd their own shop-db server at local scope for this project
The other two options (A, B)
  • AEdit the url in .mcp.json on their machine and simply never commit that change
  • BAdd their own shop-db server at user scope in ~/.claude.json
Where it went wrong: CLAUDE.local.md holds instructions for Claude to read. Which database the shop-db server connects to is not an instruction; it is a setting in the server's entry. A line of text can't change where the server connects. The fix is a second server with the same name, shop-db, added at local scope with the engineer's own database. When two scopes have a server with the same name, local wins over project, so this engineer gets their database, in this repo only. The committed .mcp.json is untouched, so teammates still get staging. User scope (B) would lose: project wins over user, so staging would still be used.
The check: before you pick a CLAUDE.md or CLAUDE.local.md line, ask: is the thing a Claude instruction (how to write code, what to call things) or a connection (which server, which address)? A memory file can only change instructions. A connection is changed by a server entry.

3 · Placeholders in .mcp.json: ${VAR} and ${VAR:-default}

The team's .mcp.json is committed, so everyone gets the same text. But people often need different values: their own API key, or their own copy of a service. A placeholder in the file is filled in on each person's machine from an environment variable when Claude Code reads it. Two forms:

  • ${VAR}: replaced by the value of the environment variable VAR. Used for secrets: the file says Bearer ${API_KEY} (a header is extra information sent with each request to an http server; Bearer is the usual word before a login key), so the key never goes into git, and each person sets API_KEY on their own machine.
  • ${VAR:-default}: replaced by VAR if it is set, and by the default text after :- if it isn't. Used when most people should get one value with no setup, and a few want their own.

This is the example from the Claude Code docs:

{
  "mcpServers": {
    "api-server": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp",
      "headers": {
        "Authorization": "Bearer ${API_KEY}"
      }
    }
  }
}

Someone who never set API_BASE_URL gets https://api.example.com/mcp. Someone who set it to http://localhost:4000 gets http://localhost:4000/mcp. Everyone's key comes from their own API_KEY, and none is written in the file.

What if a ${VAR} has no default and the person hasn't set it? The server still loads, with the text ${VAR} left in unchanged, as literal text, and claude mcp list and /mcp show a warning naming the missing variable.

Placeholders work in a server's command, args (the words after the command), env, url and headers. Don't confuse these with $ARGUMENTS, a placeholder used in skills (saved instructions you start by typing a command such as /fix-bug): it is filled in from what you type after that command, not from an environment variable.

In the question below, 3 engineers wanted their own catalog service, and everyone else the shared one with no setup. You picked a file that doesn't exist. ("Shell" in option A means the person's terminal, where environment variables are set.)

D2/D3 Paper 4, 21 Oct, question 10

Your committed .mcp.json points the catalog server at the team's shared catalog API through a hard-coded url. 3 engineers who work on the catalog want to point it at their own local API while they work, and everyone else should keep the shared one with no setup. Today those 3 edit the file and keep forgetting to undo it. What should the url be?

✗ Your pick: DThe shared API, plus a committed .mcp.local.json that Claude Code reads first
✓ Correct: B${CATALOG_URL:-https://catalog.internal}, with the shared API as the default
The other two options (A, C)
  • A${CATALOG_URL}, with every engineer setting it in their own shell
  • CThe shared API, plus a same-named server in the 3 engineers' ~/.claude.json
Where it went wrong: there is no .mcp.local.json. The Claude Code docs list three scopes for your servers, local, project and user, stored in two places: .mcp.json for project, and ~/.claude.json for local and user. The option named a file that sounds right because CLAUDE.local.md and settings.local.json exist, but MCP has no file like that. The correct answer puts a placeholder with a fallback in the committed file: ${CATALOG_URL:-https://catalog.internal}. For the 3 engineers who set CATALOG_URL on their machine, it becomes their own API. For everyone else it becomes the shared API, with nothing to set up and nothing to undo.
The check: "everyone gets X with no setup, a few want their own" → ${VAR:-X}. "Each person has their own secret" → ${VAR}, with no default.

4 · Check what actually connected

Three commands show you what Claude Code found:

CommandWhere you type itWhat it shows
claude mcp listYour terminalYour configured servers, each with a status: ✔ Connected, ✘ Failed to connect, ! Needs authentication (needs you to log in), or ⏸ Pending approval. Also the warnings from sections 2 and 3: a name set up in two scopes with different urls or commands, or a missing variable.
claude mcp get shop-dbYour terminalThe details of one server, and on a failure, why it failed.
/mcpInside a Claude Code sessionEach server's status, and the number of tools each connected server offers.

Pending approval matters for team servers. For safety, Claude Code asks each person before it uses a server from a project's .mcp.json. Until they say yes, the server shows ⏸ Pending approval (run `claude` to approve) and its tools aren't there. Running claude in the project shows the question.

The exam guide adds one fact here: tools from all the connected servers are found when Claude Code connects, and the agent can use all of them at once. A team server and your personal server don't take turns.

5 · Two things that don't exist

Twice on that paper you picked a setting that sounds real but isn't in Claude Code. The first was a committed .mcp.local.json file "that Claude Code reads first", in the catalog question (question 10) in section 3. There is no such file: MCP servers are saved only in .mcp.json (project) and ~/.claude.json (local and user). The second, in the question below, was an override: true line meant to make one CLAUDE.md replace another. "Frontmatter" is a short block of settings between two --- lines at the very top of a file; CLAUDE.md files have no override setting there or anywhere else.

D2/D3 Paper 4, 21 Oct, question 15

The root CLAUDE.md says 'Store prices as integers in pence'. The team that owns app/Legacy/ added app/Legacy/CLAUDE.md saying 'Prices here are decimals in pounds', expecting it to replace the root rule inside that folder. When Claude edits files in app/Legacy/, 1 in 4 of its changes now mixes the two formats. What should the team change?

✗ Your pick: BAdd override: true to the frontmatter of app/Legacy/CLAUDE.md
✓ Correct: AReword the root rule to name app/Legacy/ as the exception, with its own format
The other two options (C, D)
  • CMove the legacy rule into the root CLAUDE.md, under an app/Legacy heading
  • DPut the legacy rule in a CLAUDE.local.md inside app/Legacy/ instead
Where it went wrong: CLAUDE.md files have no override setting. The Claude Code docs say all the CLAUDE.md files Claude finds are added together, not used to replace each other. So in app/Legacy/, Claude reads both rules at once: pence from the root file, pounds from the folder file. When two files disagree, the docs say Claude may pick either one, with no fixed rule. That fits the 1 in 4 mixed changes. The fix is to make the files stop disagreeing: the root rule says pence everywhere except app/Legacy/, which uses pounds.

Why do these feel real? Similar names exist: CLAUDE.local.md, .claude/settings.local.json (a file of your own Claude Code settings for one project, such as permissions), and "local scope". But each "local" thing is its own feature with its own home. One more trap from the Claude Code docs: .claude/settings.local.json is a general settings file, and local-scope MCP servers are not saved in it. They go in ~/.claude.json.

The check: if an option names a file or setting you have never seen in the docs or these lessons, treat that as a reason to doubt it, not as a clever trick you missed.
