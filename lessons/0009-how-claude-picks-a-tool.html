How Claude picks a tool

The description is the only thing the model knows about your tool. Fix misrouting where the model reads.

The one question for every 2.1 stem: what did the model read just before it picked the wrong tool?

An everyday example. A temp starts on the front desk. There are two trays, labelled only "Mail" and "Post". The boss has stuck a note on the screen: "Anything about money goes in Mail." By lunch, invoices are in the right tray, but so are refund complaints, and fan letters that mention prize money. The temp isn't careless. They're doing exactly what the labels and the note told them. There are two ways to fix it. If the labels are vague, rewrite them ("Mail: invoices from suppliers. Not complaints, they go to Post."). If the labels are already clear but one word keeps sending things to the wrong tray, the note is the problem. Take it down.

Claude choosing a tool is the same. It never sees your code. It sees only each tool's name and description, plus your system prompt, all in one block of text. So when it picks wrong, the cause is something it read.

1 · What the model sees

When you send a request with tools, the API does not hand the model your code. It builds one prompt out of three things: the tool definitions as JSON Schema, your own system prompt, and the tool configuration (Define tools · Tool use system prompt). The skeleton the docs publish:

In this environment you have access to a set of tools ...
Here are the functions available in JSONSchema format:
{{ TOOL DEFINITIONS IN JSON SCHEMA }}
{{ USER SYSTEM PROMPT }}
{{ TOOL CONFIGURATION }}

Two consequences follow, and the whole of 2.1 hangs on them.

  1. A tool is its name, description and schema, nothing else. The model never sees the implementation. If the description does not say what an input looks like or when not to use the tool, the model has to guess. Anthropic's docs put it bluntly: detailed descriptions are "by far the most important factor in tool performance."
  2. Your system prompt sits in the same prompt as the descriptions. An instruction there that names a tool, or ties a word to one, is read alongside the descriptions on every turn. The exam guide's version: keyword-sensitive instructions "can create unintended tool associations" that override well-written descriptions (guide §2.1).
Misrouting is a reading problem. Ask what the model read that led it there: a thin description, two descriptions that overlap, one tool hiding several jobs, or a system-prompt line pulling the other way.

2 · What a description has to carry

The docs list four things every description should explain, and suggest at least 3–4 sentences each (Best practices for tool definitions). The exam guide adds input formats, example queries, edge cases, and boundaries against similar tools. Merged, that gives a five-point checklist. Here it is applied to lookup_order from drill Q1:

// before — what Q1's agent saw
"description": "Looks up an order"

// after
"description": "Returns one order's status, items, amounts and shipping
  events. Input: order_id, exactly 10 characters, e.g. ORD8812041
  (no '#', no spaces). Use when the customer has given an order ID.
  If you only have an email or name, call search_orders first;
  it returns candidate order IDs. Does not return payment card
  details or refund eligibility."

Parameter names are part of the description. Anthropic's tool-writing guide gives the example of naming a parameter user_id instead of user, and reports that precise refinements to tool descriptions were part of how Claude Sonnet 3.5 reached state-of-the-art on SWE-bench Verified (Writing effective tools for agents).

3 · Four causes, four fixes

Every 2.1 question describes a misrouting symptom. Your job is to find which of four causes the stem describes, then pick the fix that goes with it. The evidence is in the numbers, especially where the errors cluster.

What the stem showsCauseDesigned fix
One-line descriptions; errors spread across many requestsThin descriptionExpand with the five-point checklist
Two tools whose descriptions could both claim the same request (analyze_content vs analyze_document)OverlapRename and rewrite to a distinct purpose (analyze_content → extract_web_results); prefix by service when servers collide (jira_search)
One tool doing several jobs whose outputs must differGeneric toolSplit into purpose-specific tools with their own input and output contracts
Descriptions already fixed; leftover errors cluster on one phraseSystem prompt keywordReword the system prompt so no instruction ties a word to a tool

Your Q3 miss is the last row. Re-read the stem as evidence:

Already fixed "Two weeks ago you rewrote both descriptions … misrouting fell from 31% to 19% and then stopped improving." Row 1 has been done; doing more of it will not help.

Clustered "In 17 of every 19 remaining misroutes, the request contains 'analyze the content of'." The errors share a phrase, not a document type.

Cause named "Whenever content needs analysis, start with your content analysis tool." That phrase triggers that line.

Your pick Few-shot examples add more text to the same prompt while the conflicting line stays in place. They might lower the rate; they cannot remove the cause. That is the probabilistic trap.

4 · Split or consolidate? Both are right, in different places

The current docs also say "consolidate related operations into fewer tools", for example one tool with an action parameter instead of create_pr, review_pr and merge_pr. The exam guide says to split a generic analyze_document into three. They do not contradict each other. My synthesis of the two sources, not a sentence from either:

Consolidate (one tool, action parameter)Split (several tools)
SignalSame resource, same kind of input and result; only the verb changesDifferent jobs whose outputs must have different shapes
WhyFewer near-identical tools for the model to choose betweenNo single description or output schema can be precise for all the jobs
ExamplePR create / review / mergeextract data points · summarize · verify a claim

On the exam, follow the guide. When a stem shows one generic tool producing the wrong shape of output for one of its jobs, the answer is to split it. That was drill Q4, which you got right.
