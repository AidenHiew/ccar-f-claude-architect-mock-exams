CCA Foundations · Lesson 10 · Domain 2 · Task statement 2.3

Who gets which tools, and when they must call one

Scope the tool set per agent. Then use tool_choice per request, not per pipeline.

The one question for every 2.3 sequencing stem: does the API make this step happen first, or am I only asking nicely, and is the force still on after the step is done?

An everyday example. You're teaching someone a recipe. The onions have to be chopped before anything goes in the pan. You could write "chop first" at the top of the recipe. Usually that works, but sometimes they start frying anyway. Or you could stand beside them and hand over only the knife until the onions are done. That guarantees the order. But if you keep handing over only the knife after the onions are chopped, they can never pick up the pan, and dinner never happens. Force the first step, then hand the kitchen back.

In the API, "hand over only the knife" is tool_choice naming one tool. It is set on each request, and an agent loop sends a new request after every tool result. So you can force turn one and switch back to auto afterwards.

Exception, kept for last: if a tool call must happen but the model should choose which tool (for example, one of three extraction schemas), use any, not a named tool. Section 2 has all four settings. Section 1 starts with a different question: which tools each agent should have at all.

1 · Fewer tools, chosen for the role

Lesson 9 showed that every tool's description goes into the prompt on every turn. Each extra tool is one more candidate the model has to rule out. The exam guide states the result: giving an agent 18 tools instead of 4–5 makes it pick the right one less reliably, because it has more options to weigh, and agents given tools outside their specialization tend to misuse them, for example a synthesis agent that starts running web searches (guide §2.3). Anthropic's tool-writing guide says the same from the other side: "too many tools or overlapping tools can also distract agents" (Writing effective tools for agents).

The guide gives three moves. Each one keeps what the agent needs and removes what it can misuse:

MoveWhen the stem showsGuide example
Scope each agent to its role's toolsAn agent with many tools using some outside its job4–5 tools per subagent, not 18
Add a narrow cross-role tool for a frequent need, and send the rare complex cases through the coordinatorFrequent round trips to the coordinator for simple lookupsverify_fact for the synthesis agent (85% simple checks); the 15% that need deep research still go through the coordinator
Constrain a generic toolA needed tool used for things it should not dofetch_url → load_document that validates document URLs (drill Q6, which you got right)

Look at what the wrong answers do instead: give everything to everyone ("to be safe"), take the tool away entirely so every use becomes a coordinator round trip, or keep the tool and add an instruction. The guide's answer sits in the middle: least privilege, with the frequent case kept local.

2 · The four tool_choice settings

From Define tools · Forcing tool use:

SettingThe model must…Use when
{"type": "auto"}decide: call a tool, or reply in text. Default when tools are providedConversation, where a text reply is sometimes the right answer
{"type": "any"}call one of the tools; it picks whichA text reply would break the downstream step, and the model should choose among several schemas (drill Q7)
{"type": "tool", "name": "x"}call exactly tool xYou know which step must happen now, such as a prerequisite
{"type": "none"}not call any tool. Default when no tools are providedA turn that must be text only

One detail that shows up in distractors: with any or tool, the API prefills the assistant turn to force the tool call, so the model "will not emit a natural language response or explanation before tool_use content blocks, even if explicitly asked to do so." If you need an explanation as well as the call, use auto and ask for the tool in the user message.

3 · Sequencing: force the first step, then hand back the choice

This is the half of objective 29 you missed. The key fact is that tool_choice is a parameter of each API request. An agentic loop sends a new request after every tool result, so each turn can have its own setting. Here is drill Q8's pipeline done correctly:

Request 1 · tool_choice: {"type":"tool","name":"extract_metadata"} → the model must call extract_metadata. You run it and append the tool_result: vendor name and amounts are now in the conversation.
Request 2 · tool_choice: {"type":"auto"} → the model reads the real vendor name and calls lookup_vendor with it. Nothing is guessed.
Request 3 · auto → it calls classify_spend, then finishes with end_turn.

Now your pick, forcing extract_metadata on every turn:

Request 1 · forced → extract_metadata. Fine.
Request 2 · forced again → the model must call extract_metadata again. lookup_vendor is never allowed.
Request 3…n · the same, until your iteration cap stops the loop. The pipeline never reaches enrichment.
Forcing guarantees the next call. Use it for the turn that must happen first, then return the choice to the model, because the dependent steps need tools that a forced setting does not allow.

Why the other Q8 options fail

any on every turn guarantees that some tool is called, not which one, so lookup_vendor can still come first. A numbered instruction in the system prompt is the control that was already failing 11% of the time. Neither one guarantees the order.

4 · What changed in the current docs (for real-world use)

The docs now list models where forced tool use is not supported: on Claude Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1, any and tool return a 400 error. The recommended replacement is auto with strict tool use, or structured outputs when you need a fixed JSON shape. The exam guide (v0.2) still tests any and forced selection as described above. Answer the exam from the guide. Keep the change in mind for real builds. It is also why notes/domain-2 flags it in the traps table.
