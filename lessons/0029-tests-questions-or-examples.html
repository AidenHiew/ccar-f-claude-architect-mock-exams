Tests, questions or examples?

Between 20 and 25 October you lost 7 questions on two topics, across 5 practice papers. This page shows all 7 in full; you don't need to remember any of them. Part 1 has 3 about which way to improve Claude's code (one of them you saw in Lesson 28). Part 2 has 1 about fixing several problems at once or one at a time. Part 3 has 3 about what to add to a prompt when rules aren't working.

Two topic numbers from the exam guide (the official guide that lists what the exam tests) are on this page. 3.5 is improving Claude's work round by round in Claude Code. 4.2 is putting examples in a prompt. They are your last 2 weak topics. On your September exam score report, the 3.5 objective came back at 25%.

The plain question. Claude's output is wrong, or might be. What is missing: the cases to check, the knowledge of what the cases even are, or a picture of what right looks like?

An everyday example. You're ordering a cake.

  • You know exactly what it should look like. Words keep getting it wrong ("3 tiers, not 3 layers"), so you show the baker a photo. That's examples.
  • You have a list of must-haves: gluten-free, serves 40, ready by 2 pm. You check the cake against the list before you pay. That's tests.
  • You've never ordered a wedding cake. You don't know what you don't know: will it melt in a marquee in summer? How does it travel? You let the baker ask you questions first. That's the interview.
The one idea: name what is missing, then pick the fix that supplies it.
• The cases are known and listed → write tests first.
• You know the right output, but words keep failing → show input/output examples.
• Nobody knows the cases yet (a new area) → have Claude interview you.
For prompts (4.2): no rules written yet → write the rules. Rules written, and new cases still slip past → 2–4 hard cases, each with the reason. And when a stem asks what to add to the prompt, an option that sends cases to a person is not a prompt change.

Words to start with

Stem
The question's own text, above the four options.
Prompt
The written instructions given to the model for a task.
Tests first, share the failures
Write a set of automatic checks (a test suite) for what the code must do, before Claude changes it. Run them on each new version and paste the ones that fail back to Claude, until all pass.
Edge case
An unusual input that code must still handle, such as a public holiday or an empty field.
Input/output examples
A few real inputs, each with the exact output it should become. They show Claude the change instead of describing it.
The interview pattern
Before building, you ask Claude to question you: what could fail, what happens in odd cases, what the business cares about. It brings out things you hadn't thought of. The exam guide's examples are failure modes and cache invalidation (when stored copies of data go stale), in an area that is new to the developer.
Plan mode
A Claude Code mode where Claude explores the code and writes a plan, and edits nothing until you approve it. It plans how to build; it never runs or checks anything (Lesson 28).
Few-shot examples
Worked examples written into the prompt itself: an input, the right answer, and (for hard cases) why that answer and not the others. It is the same idea as input/output examples, used in a prompt instead of a coding chat.
Rules (the guide also says "explicit criteria")
Lines in the prompt that say what counts, for example which kinds of code change to flag and which to skip. Lesson 27 covers when to write them.
Consistency on 2 runs
Run the same document through twice; how often both runs give the same answer. A low number means the model is unsure on those cases.

Words that appear in the past questions (you need these only to read the questions):

  • Webhook: a message one company's system sends to yours when something happens, such as "refund failed".
  • Merchandising team: the people who plan which products to promote. Demand model: code that predicts how much will sell.
  • Portal, column header, query, help footer: parts of a web app: a page, a table heading, a database lookup, the links at the bottom of a page.
  • In production: in the live system. ms: milliseconds (1,000 ms = 1 second).
  • Tie-break rule: a rule for which answer wins when a report fits more than one. Assessor: a person who checks insurance claims.
  • Subagent: a second Claude run that the main agent gives one job to.
  • Fuel surcharge, port fees: kinds of charge on a shipping invoice. "BAF" is a fuel charge.

The tell between tests and the interview is one question: could you write the test? If the stem lists the cases, yes, so write them. If the stem says the developer is new to the area and the misses were things nobody thought of, no: you can't write a test for a case nobody has thought of. That is the interview's job.

D2/D3 Paper 2, 20 Oct, question 29

A developer who has never worked on retail forecasting must add promotion handling to the demand model. The ticket says only 'account for promotions'. On a similar ticket last quarter, the first version missed 2 effects the merchandising team cared about and was rewritten twice. The developer can't yet say which promotion effects matter. What should the developer do first?

✗ Your pick: DGive Claude 3 examples of promotion weeks and the expected output
✓ Correct: BAsk Claude to interview them about promotions before any code
The other two options (A, C)
  • AAsk Claude to implement it from the ticket, then review the result
  • CWrite tests first for the promotion cases they already know about
Where it went wrong:
  • What is missing here is knowledge: the developer can't yet say which promotion effects matter, and last quarter the first version missed 2 effects nobody had thought of.
  • Examples (your pick) show Claude a change you can already describe: this input should become that output. You can't write the expected output for an effect you haven't thought of yet.
  • B, the interview: Claude asks you questions before writing any code (what counts as a promotion, what happens to demand the week after, and so on). That is how the effects nobody listed come out before the build, not after it.

Weak Rows Paper 4, 25 Oct, question 13

A developer who has never worked with payment webhooks must add refunds for cancelled concerts through the payment provider. Last week, in plan mode, Claude wrote a plan the developer approved, but testing showed it missed that the provider can send the same webhook twice and that a refund can fail 1 hour after it starts. Neither had occurred to the developer. How should they start the next feature in this area?

✗ Your pick: CWrite tests for the refund flow first, then share the failures
✓ Correct: BHave Claude ask them about failure cases before it builds anything
The other two options (A, D)
  • AUse plan mode again, with a longer description of the refund flow
  • DGive Claude 2 example refunds with the expected result of each
Where it went wrong:
  • The two failures (the same webhook sent twice, a refund failing an hour in) were ones the developer didn't know could happen. The next feature will have more like them.
  • Tests first (your pick) only check the cases you write down. Nobody writes a test for a duplicate webhook they've never heard of, so the tests would pass and the gap would stay.
  • Plan mode (A) was already tried: the approved plan missed both failures, because a plan is built from what the developer asked for.
  • B, the interview, is what brings the unknown cases out: Claude asks about failure cases before it builds anything.

Now the same line from the other side: a question where the cases were known, so tests were the answer and plan mode was your pick.

Weak Rows Paper 3, 24 Oct, question 15

A developer wants Claude to rewrite the delivery-slot allocation function to run in under 50 ms for 5,000 orders; it takes 900 ms today. The function has about 30 edge cases, including order cut-off times, public holidays and drivers' maximum shifts. Last quarter a faster version from Claude broke public-holiday handling, and the break was found in production. How should the developer approach the rewrite?

✗ Your pick: CUse plan mode to have Claude design the faster algorithm before coding it
✓ Correct: AWrite tests for the edge cases and the 50 ms target first, then share failures
The other two options (B, D)
  • BGive Claude 3 orders with the exact slots each should get, holidays included
  • DAsk Claude to explain in prose how its new version handles each edge case
The other side of the same line (you saw this card in Lesson 28):
  • Here the cases are known: about 30 edge cases, named (cut-off times, public holidays, drivers' maximum shifts), plus a 50 ms target. Nothing needs asking about.
  • What went wrong last time was a break nobody noticed until it was live. Only running tests catches that: write tests for the 30 cases and the 50 ms target first, run them on each new version, and paste the failures back to Claude.
  • Plan mode (your pick) designs the algorithm but never runs anything. The interview would ask questions the team can already answer.
The check: before the options, finish the sentence "The cases are ___": "listed in the stem" (tests first), "known, but Claude keeps misreading them" (input/output examples), or "not known yet, the area is new" (the interview).

Part 2 · All in one message, or one at a time? (3.5)

When review finds several problems, the stem tells you whether the fixes touch each other.

The stem saysDo thisWhy
"All 3 change the same steps", "fixing one changes where the others go"Describe all of them in one detailed messageFixed one at a time, each fix would undo or clash with the last.
"Different files", "don't affect each other", "check each fix before moving on"Fix them one at a time, checking eachEach fix is small and can be checked on its own.

D2/D3 Paper 4, 21 Oct, question 28

After a release, a developer found 3 problems in the portal: a misspelt column header on the results page, a slow query on the audit screen and a broken link in the help footer. They are in different files and don't affect each other. The developer wants each fix checked before moving on. How should they raise them with Claude?

✗ Your pick: CIn 3 parallel sessions, all started at the same time
✓ Correct: BSeparately and in turn, checking each of the 3 fixes first
The other two options (A, D)
  • AAll 3 in one detailed message, handled as a single task
  • DThe slow query in plan mode, then the other 2 together
Where it went wrong:
  • The 3 problems don't touch each other: different files, and fixing one changes nothing about the others. Separate problems are fixed one at a time.
  • 3 sessions at once (your pick) means 3 setups for 3 small fixes, and none is checked before the next starts. The stem asked for each fix to be checked before moving on.
  • B: raise them in turn and check each fix before the next.
  • The opposite case is when the fixes do affect each other (fixing one changes where the others must go). Then you describe all of them in one message, so Claude can fix them together.

Part 3 · What to add to the prompt (4.2)

4.2 questions describe a model making uneven decisions and ask what to add to the prompt. Read two things in the stem: were rules already tried? and what does the question ask for?

What the stem showsAdd to the promptNot
Only a vague line ("flag risky changes"); nobody has written down what countsThe rules: what to flag and what to skip (4.1, Lesson 27)Examples first. Without written rules, they show cases but never say where the line is.
Rules written, a new rule barely moved the number, and new cases keep slipping past2–4 hard cases, each with the answer and why not the othersAnother rule; many easy examples; a score the model gives itself
The format of the output varies even though the prompt describes it2 or so complete outputs in the exact formatThe description repeated, or written louder
A field comes back empty on documents laid out differentlyExamples of those other layouts, with the value foundMaking the field required. That forces an answer, which invites made-up values.

The person trap. Sending hard cases to a person is a real fix. It belongs to a different exam topic (Domain 5, human review), which is about which cases people should check. But when the question asks "what should you add to the prompt?", a step that routes cases to a person isn't something you write into a prompt, so it is out. This is the pick on two of the three cards below.

Representative Mock 2, 22 Oct, question 11

The system prompt lists 9 rules for when a damaged box earns a full refund, a partial credit or a replacement. On mixed cases the agent applies them unevenly: in a review of 150 chats where one item was spoiled and the rest were fine, the same situation got all three outcomes. A 10th rule added last week made no difference. What should the team add?

✗ Your pick: AA severity score from 1 to 10 the agent assigns before choosing an outcome
✓ Correct: C3 worked mixed cases, each showing why one outcome beat the other two
The other two options (B, D)
  • BAn 11th rule ranking the 3 outcomes for boxes with more than one problem
  • DA refund_decision subagent that applies the 9 rules to each damaged box
Where it went wrong:
  • Rules were written (9 of them), a 10th made no difference, and the mixed cases are still decided unevenly. That is the moment for examples: 2–4 worked mixed cases, each showing why one outcome beat the other two.
  • A severity score the agent gives itself (your pick) is one more judgement it makes unevenly. It doesn't show the agent what a right decision looks like.
  • B, an 11th rule, is more of what already failed.

Weak Rows Paper 3, 24 Oct, question 30

The pipeline classifies each claim's cause of loss as drought, frost, hail or other. Last month the team added 8 tie-break rules for reports that mention more than one cause, and the share of mixed reports that get the same cause on 2 runs rose only from 75% to 78%. Assessors keep finding mixed cases, such as frost damage on a crop already stressed by a dry month, that no rule settles. What should you add to the prompt?

✗ Your pick: DA step that sends each mixed report to an assessor to pick the cause
✓ Correct: A3 mixed reports, each with the cause chosen and why not the others
The other two options (B, C)
  • BA ninth tie-break rule for frost damage on a crop stressed by drought
  • C20 examples: 5 clear-cut reports for each of the 4 causes
Where it went wrong:
  • The question asks what to add to the prompt. A step that sends reports to an assessor is not something you write into the prompt. It hands the decision to people and leaves the model just as unsure.
  • Rules were tried: 8 of them moved consistency only from 75% to 78%, and new mixed cases keep turning up that no rule settles. So, examples: 3 mixed reports, each with the cause chosen and why not the others (A).
  • C has examples too, but of easy cases. Nothing in them shows how to decide a mixed report.
  • When we went over this question in chat on 25 Oct, you put it as: no rules → set rules; rules set and still wrong → give examples.

Weak Rows Paper 4, 25 Oct, question 18

The pipeline sorts each charge on a carrier invoice into freight, fuel surcharge, port fees or other. After 11 rules were added for charges with unclear names, the share of those charges that land in the same category on 2 runs rose only from 68% to 71%. Reviewers keep finding new names, such as "BAF adj. Q3 emergency", that no rule covers. What should you add to the prompt?

✗ Your pick: CA step that sends each unclear charge to a reviewer to pick
✓ Correct: A3 hard charge names, each with its category and the reason
The other two options (B, D)
  • BA 12th rule for charges that combine "BAF" with other words
  • D40 examples: 10 clearly named charges for each of the 4 categories
Where it went wrong:
  • The same shape as the card above, and the same pick: sending the hard ones to a person.
  • When we went over this question in chat on 25 Oct, you named the clue for A: "rules added but still no good". That is right, and it is why A beats B (a 12th rule).
  • What rules out C is the question itself: "What should you add to the prompt?" Sending charges to a reviewer isn't a change to the prompt. When a stem asks for a prompt change, any option that adds a person or a step outside the prompt is out.
The check: read the question's last line first. If it says "add to the prompt", cross out any option that adds a person, a step or a new agent. Then ask "were rules tried?": no → rules; yes, and cases still slip past → hard cases with the reason.
