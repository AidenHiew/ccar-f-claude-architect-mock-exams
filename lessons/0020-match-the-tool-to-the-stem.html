Match the tool to what the stem names

Four of your six misses on the 19 Oct mock came from the same place: the stem named something specific, and the pick answered something else.

Before you read the options, ask one plain question: what exactly does the stem name?
· If it names something small (one function, one entry point, one file for one task), pick the lightest tool that handles it completely.
· If it names a symptom (fixes keep breaking old cases, the format is read differently each run, the domain is new), pick the technique built for that symptom.
How important the system is, or how big the codebase is, doesn't change the answer.

An everyday example. A cupboard door in a hospital's operating theatre squeaks. The hinge screw is loose, and you can see which one.

  • The right move: tighten that screw, then open and close the door to check it. Done in two minutes.
  • The tempting move: "It's an operating theatre, it's critical, so let's get an architect to survey the whole wing first." The survey takes a week, and it ends with the same screw being tightened.

The theatre being important is a reason to check the door properly afterwards. It isn't a reason to survey the wing. An architect is right when you're moving walls, not when you can point at the loose screw.

Where this has cost you points. Here are three questions from the 19 Oct mock, in full, with your pick and the correct answer. A fourth, about refinement, is in section 3.

Where it went wrong: "business-critical" says how much the service matters, not how big the change is. The stem names one line, one function and a stack trace. Representative mock, 19 Oct, Q43

An engineer asks how a booking cancellation flows from the API to the refund. The agent's first move was to Read all 220 files under app/, and by file 140 its context was full and its answers became vague. The cancel endpoint is a single controller action. How should the agent explore instead?

✓ Correct: CGrep for the cancel action's route or method name, Read that action, then follow its calls

All three picks were real tools, used for real jobs, just not this job. In each one the stem pointed at something small: one function with a stack trace, one controller action, one log for one investigation. Each pick added something on top: a planning phase, reading the whole app, or a committed rule file.

1 · Three jobs, light to heavy

For each kind of job there's a light tool and heavier ones. The heavier tools aren't worse. They're built for bigger jobs, and the stem tells you when you have one. Green is the correct answer, red is your pick.

LighterHeavier

Changing code (3.4, mock Q24)

LightDirect execution: make the change, with a test✓ Correct for Q24
HeavierPlan mode first: Claude reads and plans without editing, you approve, then it edits✗ Your pick
HeaviestPlan mode, with an Explore subagent for the discovery phase

Heavier is right when the stem names: many files (the guide's example is 45+), more than one valid approach, an architectural choice, or code you're unfamiliar with.

Finding your way in code (2.5, mock Q43)

LightGrep for the entry point, Read it, then follow the calls✓ Correct for Q43
HeavierAn Explore subagent for a long discovery phase, returning a summary
HeaviestRead every file up front, in the main session or in a subagent✗ Your pick

Heavier is right when the stem names: a long, verbose discovery phase with no known starting point, in a multi-phase task where that output would fill the main context. "Read everything up front" is the pattern the guide says to avoid.

Giving Claude context (3.1 and 3.3, mock Q18)

Light@file in this session's prompt: this task only✓ Correct for Q18
Heavier.claude/rules/ file with paths: loads whenever Claude reads a matching file✗ Your pick
HeaviestCLAUDE.md (or a rule with no paths): loads in every session

Heavier is right when the stem names: something needed again. Needed whenever certain files are touched → a rule with paths. Needed in every session → CLAUDE.md. Needed once → @.

The Claude Code best-practices page puts the first track in one line: "If you could describe the diff in one sentence, skip the plan." The Q24 diff fits in one sentence: add a guard in ETAForStop that returns an error when the stop has no geocode.

2 · The words that pull you to the heavy end

Distractors borrow their weight from words in the stem that describe the surroundings, not the job. Learn to spot them:

Stem wordWhat it describesWhat it actually changes
"business-critical", "regulated", "production" (Q24)How much the system mattersHow carefully you check the change. That's why Q24's answer includes a test. It doesn't make a one-line change need a plan.
"220 files", "a large codebase" (Q43)How big the codebase isNothing, if the stem also names a starting point. You follow one path through the code, not all 220 files.
"900 lines", "committed", "a teammate suggests" (Q18, Q24)The size of the file, or someone's opinionNothing. A big log needed once is still needed once. A teammate's suggestion is part of the setup, not a fact about the task.

One check on Q43's pick. A subagent is the right tool for keeping noisy reading out of the main conversation. The best-practices page recommends one for broad investigations. But a subagent changes where the reading happens, not how much of it there is. When the stem names a starting point, the lightest correct move is to read less, not to read the same amount somewhere else.

The reverse case, so you don't overcorrect. The guide's own sample question restructures a monolith into microservices, and the answer there is plan mode, because the stem names exactly what plan mode is for. Light isn't always right. The point is to match: small job → light tool, big or uncertain job → the heavier one.

3 · Refinement: the symptom picks the move

Task statement 3.5 is the same habit in a different form. You aren't choosing light or heavy. You're choosing which of five moves fits the symptom the stem describes. Here is the mock question where this cost you a point:

Representative mock, 19 Oct, Q26

Claude is rewriting the function that rounds route distances for driver pay. Over 4 rounds of chat feedback, each fix breaks a case fixed earlier: one round broke zero-length legs, another broke distances near the 0.5 km boundary. The team knows the expected output for 15 such cases. What should the developer do?

✗ Your pick: BDescribe the 15 cases in one long prose message and ask Claude to handle them together
✓ Correct: AWrite tests for the 15 cases first, then iterate by giving Claude the failing tests
The other two options (C, D)
  • CFix the rounding by hand and ask Claude only to tidy the code style around the function
  • DGive Claude 2 input and output pairs for the hardest cases and go on as before
Where it went wrong: B tells Claude about all 15 cases once. Nothing checks them again. On round 5, a fix can break zero-length legs a third time, and no one notices until a driver is paid wrong. The stem has the two signs that call for tests: fixes keep breaking earlier cases, and the expected outputs are already known. Tests turn those 15 cases into a check Claude runs on every round.

This one was a fair trap. Lesson 18 taught that "fixing one broke another" is a sign the problems are tangled, so they go in one message. That's still true. But when the expected outputs are already known, there's a better way to bundle them: as tests. A test suite holds all 15 cases at once, like one message does, and it also re-checks every case on every round. The guide's wording is "writing test suites first, then iterating by sharing test failures".

The tie-break, so lessons 18 and 20 agree: fixes keep breaking each other and the expected outputs are known → tests. Fixes keep breaking each other but you can't yet write down the expected outputs → one detailed message, as in lesson 18. "The team knows the expected output for 15 such cases" is what moves Q26 from the message to the tests.

The full lookup, with each move's signal in the stem:

What the stem saysThe moveLesson
Fixes keep breaking cases that worked before, and the expected outputs are knownWrite the tests first, then iterate by sharing the failing teststhis one
Several problems, and fixing one changes anotherOne detailed message covering all of them, saying how they connect18
Several problems that don't affect each otherOne at a time, checking each fix before the next18
A prose description of a transformation gives different output each run2–3 concrete input/output examples13
One kind of input fails (the guide's example: null values in a migration)That input, its expected output, as a specific test case13
An unfamiliar domain, and the developer doesn't yet know which design questions matterThe interview pattern: Claude asks the developer questions before it implementsthis one

The interview pattern, briefly, since it's new. The guide's example is a developer about to build something like a cache, who hasn't thought about invalidation strategies or failure modes. Instead of writing a spec they can't yet write, they have Claude ask the questions first. The best-practices page suggests a prompt like this:

I want to build [brief description]. Interview me in detail using the
AskUserQuestion tool.

Ask about technical implementation, UI/UX, edge cases, concerns, and
tradeoffs. Don't ask obvious questions, dig into the hard parts I might
not have considered.

Keep interviewing until we've covered everything, then write a complete
spec to SPEC.md.

Quoted from the Claude Code best-practices page, "Let Claude interview you". It then suggests starting a fresh session to implement the spec.

How to tell it apart from tests first: tests need you to know the expected behaviour. The interview is for when you don't know it yet. Once the interview has produced a spec, writing tests from it is a sensible next step.
