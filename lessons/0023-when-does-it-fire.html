When does it fire?

Lesson 19 gave you two questions: who gets it, and where it loads. Five of your recent misses got both right and still picked the wrong file, because the file switches on at the wrong moment.

After "who needs it?" and "which projects?", ask a third plain question: when should it switch on?
1. Every session, without anyone remembering → CLAUDE.md, ~/.claude/CLAUDE.md, CLAUDE.local.md, an @import
2. When Claude touches certain files → a .claude/rules/ file with paths
3. When someone decides to start a task → a skill
4. Just now, for this one session → say it in the prompt, and store nothing

An everyday example. Four ways to get a message to someone at work.

  • The noticeboard by the door. Everyone reads it every morning on the way in. (Every session.)
  • A sign taped to the printer. You only read it when you go to use the printer. (When certain files are touched.)
  • The recipe binder on the shelf. Nobody reads it until they decide to cook that dish. (When someone starts a task.)
  • Telling a colleague something in person, today. It's gone tomorrow, and nobody has to take a note down. (This session only.)

"Always sign your emails this way" belongs on the noticeboard, not in the recipe binder: nobody opens the binder before every email. "Today, use the second tray" is said in person; pin it to the noticeboard and people are still following it next week.

Where this has cost you points. Five questions, in full, with your pick and the correct answer. The first three picked the wrong trigger. The last two reached for CLAUDE.local.md where it doesn't fit.

D2/D3 paper, 19 Oct, Q14

An engineer wants Claude to write commit messages in their own format: a 50-character summary, then a bullet list. They work in 6 repositories, want it in all of them, and none of the teams in those repositories should be affected. They have started adding the same lines to a CLAUDE.local.md in each repository, one at a time. Where should the instruction live?

✗ Your pick: DIn a skill in ~/.claude/skills/ that they invoke before each commit
✓ Correct: BIn their own ~/.claude/CLAUDE.md, loaded in each of their projects
The other two options (A, C)
  • AIn a CLAUDE.local.md in each of the 6 repositories, kept out of git
  • CIn each repository's root CLAUDE.md, under a heading with their name
Where it went wrong: who and where were right: just me, all my projects. The miss was when. A skill runs only when someone invokes it, by typing /name or when Claude decides it's relevant. A format for every commit has to be there every session, without anyone remembering. Me × all projects × every session is ~/.claude/CLAUDE.md.

D2/D3 paper, 19 Oct, Q16

The monorepo has 5 Django apps, each with its own CLAUDE.md, and 3 standards files: api.md, testing.md and celery.md. Each app's CLAUDE.md holds pasted copies of the 1 or 2 standards that apply to it, and after 4 months the copies differ from the originals in 9 places. Only the 2 apps that run background jobs need celery.md. What is the best way to organise this?

✗ Your pick: CTurn each standards file into a skill that engineers run when they start work in an app
✓ Correct: AHave each app's CLAUDE.md @import just the standards files that apply to it
The other two options (B, D)
  • BPaste the 3 standards into the root CLAUDE.md, under headings that name their apps
  • DKeep the copies and add a CI check that fails when an app's copy differs from the original
Where it went wrong: the real problem was drift between copies, and a skill does fix the copies. But it changes when the standards apply: only when someone remembers to run it. Standards must hold whenever Claude works in the app, so they stay every-session. @import keeps them every-session and gives one source: each app's CLAUDE.md pulls in just the files it needs, and they load with it.

Lesson 21 quiz, 19 Oct, Q6

A 250-line checklist for cutting a release sits in the root CLAUDE.md. Releases happen about once a month, when someone decides to start one, and they aren't tied to editing any particular files. Where should the checklist go?

✗ Your pick: AA .claude/rules/ file with paths set to release/** for the checklist
✓ Correct: DA project skill, /cut-release, that people run to start a release
The other two options (B, C)
  • BAn @import of a release.md file from the root CLAUDE.md instead
  • CA CLAUDE.md in the release/ folder, loaded when Claude works there
Where it went wrong: the mirror image of Q14 and Q16. A paths rule fires when Claude reads or edits a matching file. A release starts when a person decides to start one, and the stem says it isn't tied to any files. Something that starts with a person's choice is on demand: a skill.

D2/D3 paper, 19 Oct, Q7

One of your 14 engineers wants to try an experimental profiling MCP server that is still unstable. They want it in all 4 repositories they work in, and no teammate should see it or be asked to approve it. The warehouse repository already has a committed .mcp.json with 3 team servers. Where should the server be configured?

✗ Your pick: DIn a CLAUDE.local.md in each of the 4 repositories, as the server's launch command
✓ Correct: BAt user scope in their own ~/.claude.json, added once with claude mcp add --scope user
The other two options (A, C)
  • AIn the warehouse repo's committed .mcp.json, with its entry marked as experimental and optional
  • CWith claude mcp add run from inside the warehouse repo, leaving the scope at its default setting
Where it went wrong: two things. CLAUDE.local.md holds instructions; Claude Code never starts an MCP server from it. And it covers one repository, so four copies for “all my repositories”. MCP has its own copy of the map, chosen with --scope: me × all projects is --scope user, kept in ~/.claude.json.

D2/D3 paper, 19 Oct, Q22

For a 1-day performance spike, a developer wants Claude to add timing logs around each database call in checkout/reserve.ts, and only in that file. They will try it in today's session only and then discard the changes, and from tomorrow they are back on normal work in that same file, where timing logs must not be added. A teammate suggests a .claude/rules/ file with paths set to checkout/reserve.ts. What is the best way to give Claude the instruction?

✗ Your pick: CAdd it to their CLAUDE.local.md, then delete the line after the spike
✓ Correct: BSay it in today's session prompt and name checkout/reserve.ts as the file
The other two options (A, D)
  • ACreate .claude/rules/spike.md with paths set to reserve.ts, left uncommitted
  • DCreate a /spike-timing skill in ~/.claude/skills/ and run it today
Where it went wrong: just me was right. But CLAUDE.local.md loads at the start of every session in this repo, for any file, until someone deletes the line. The instruction is for today only, and tomorrow's work in the same file must not get it. This-session-only means no file at all: say it in today's prompt.

In Q14 and Q16 something that must always apply was put somewhere that runs only when started. In lesson 21's Q6 it went the other way: something started by a person was tied to files. Q7 and Q22 picked the one file that sounds "personal", without checking what it holds or when it loads.

1 · The four triggers

Read across: when it switches on, what lives there, and the words in a stem that point to it.

Every session, at launchCLAUDE.md / .claude/CLAUDE.md, ~/.claude/CLAUDE.md, CLAUDE.local.md, anything they @import, a rules file with no paths. MCP servers too: they're there in every session in their scope."always", "every commit", "standards", "conventions", "preference", "whenever Claude works in…"
On file access, when Claude reads or edits a matching fileA .claude/rules/ file with paths; a CLAUDE.md inside a subfoldera kind of file ("every *.sql"), a folder, "only when editing…", spread across many directories
On demand, when someone starts itA skill: you type /name, or Claude judges it relevant to your request"when someone decides", "once a month", a workflow, a checklist, "run it", "isn't tied to any files"
This session onlyWhat you type in the prompt, including @path/to/file"today", "one investigation", "then discard", "tomorrow, back to normal"

Two details from the docs that the misses turned on:

  • @import loads at launch, together with the CLAUDE.md that names it. It doesn't make anything on-demand. It just lets one file be the source for many (Q16).
  • A skill's body loads only when it's used. That's its strength for a long checklist, and why it's wrong for a rule that has to hold on every commit (Q14).

It's the same grid as instructions: local matches CLAUDE.local.md, project matches CLAUDE.md, user matches ~/.claude/CLAUDE.md. But the files don't swap. An MCP server only ever goes in an MCP location, which is the first thing wrong with Q7's pick.

4 · What CLAUDE.local.md is, and isn't

It is instructions, for me, in this one repo, in every session, until I delete them. Each part of that rules something out:

  • Instructions: not MCP config (Q7), not a skill (mock Q19).
  • This one repo: not "all my repositories" (Q7, Q14's option A). That's ~/.claude/CLAUDE.md, or --scope user for a server.
  • Every session, until deleted: not a note for today (Q22). That's the prompt.

When a stem has two constraints, such as "in all 4 repositories" and "no teammate should see it", check the pick against each one in turn before moving on. In Q7, CLAUDE.local.md passed the second and failed the first.
