Who gets it, and where does it load?

Every "where should this go?" question in Claude Code has the same answer key, once you ask two plain questions in order.

Before you read the options, answer two questions about the thing being set up:
1. Who needs it? The whole team, or just me?
2. Where should it load? In this project only, or in all my projects?
The two answers point to one box on the map below. The right option is the file in that box.

An everyday example. You work in a team office, and you also visit other offices.

  • The team noticeboard in this office. Everyone in the office reads it. It doesn't follow you anywhere. (Team, this place.)
  • A sticky note on your own desk in this office. Only you see it, and only when you sit here. (Me, this place.)
  • The notebook in your bag. Only you read it, and it comes to every office you visit. (Me, everywhere.)

A reminder about your own login for this office goes on the sticky note. Put it on the noticeboard and the whole team reads it. Put it in the notebook and you carry it to offices where it means nothing. Claude Code has the same three places, for instructions, for skills and commands, and for MCP servers.

Where this has cost you points. Here are the four questions in full, as you saw them, with your pick and the correct answer.

D3 quiz, 16 Oct, Q3

A developer on a 9-person team wants Claude to know their personal staging sandbox URL and that they like verbose test output. Both apply only to this repository. Teammates must not see these notes, and the developer's other repositories must not pick them up either. Where should the notes go?

✗ Your pick: BIn ~/.claude/CLAUDE.md, which is only ever loaded by this developer's own sessions
✓ Correct: CIn a CLAUDE.local.md at the project root, which stays out of version control
The other two options (A, D)
  • AIn the project's root CLAUDE.md under a section headed with this developer's username
  • DIn a personal skill in ~/.claude/skills/ that the developer invokes in each session
Where it went wrong: "who" was right (just me) but "where" was wrong. ~/.claude/CLAUDE.md loads in every repo you open, and the stem says the other repos must not pick the notes up. Me + this project is CLAUDE.local.md.

D2 Paper 2, 16 Oct, R09

Your team's project .mcp.json, committed to the repo, configures the community Jira MCP server with its token written as ${JIRA_API_TOKEN}. Eleven engineers use its 9 tools daily. A new engineer cloned the repo yesterday and skipped the onboarding step that sets team environment variables, and Claude Code shows no Jira tools in their sessions. What should they do?

✗ Your pick: BCopy the Jira server entry into their own user-level ~/.claude.json with their token written in directly, then restart Claude Code
✓ Correct: ASet JIRA_API_TOKEN in their own environment, restart Claude Code, then confirm in /mcp that the Jira server and its tools appear
The other two options (C, D)
  • CReplace ${JIRA_API_TOKEN} in .mcp.json with a shared team token and commit it, which keeps everyone's setup consistent
  • DExpand the Jira tool descriptions in .mcp.json, which helps Claude Code discover and prefer the Jira tools over built-ins
Where it went wrong: the shared server was already in the right box (team, this project), and it worked for the other eleven. Only one machine was missing its environment variable. Copying the server into a personal file moves it to the wrong box, and writing the token in directly is the thing ${VAR} exists to avoid.

Every pick put the thing in a real, working place, just the wrong box. Q3 got "who" right and "where" wrong. Q19 got "who" right but chose a file that holds the wrong kind of thing. Q40 and R09 got "who" wrong because a token was involved. Section 2 covers that pull.

1 · The map

Rows are who, columns are where. Each box lists what lives there.

No box for this in a repo. A team-wide setup that follows people into every project isn't something a repo can do. (Organisations have a managed policy file for that; the exam guide doesn't test it.)
Just me
never committed
Instructions: CLAUDE.local.md at the project root (you add it to .gitignore) MCP servers: local scope, the default when you add a server (kept in ~/.claude.json under this project) Only your sessions, only in this repo.
Instructions: ~/.claude/CLAUDE.md Skills: ~/.claude/skills/ Commands: ~/.claude/commands/ MCP servers: user scope, in ~/.claude.json Only your sessions, in every repo you open.

A quick way to read the paths: a path starting with ~/ is yours alone, because it sits in your home folder, which no one else clones. A path inside the repo is the team's once it's committed. CLAUDE.local.md is the one in-repo file that stays yours, because the docs tell you to add it to .gitignore so it's never committed.

The exam guide talks about MCP in two scopes: project .mcp.json for shared team tooling, and user ~/.claude.json for personal or experimental servers. The docs add local scope as the default. On the exam, read any ~/.claude.json option as "just me".

2 · Two things that pull you into the wrong box

Pull 1: "It needs a secret, so it must be personal." It doesn't follow. A token is personal, but the server can still be the team's. .mcp.json supports environment-variable expansion, so the shared file names the variable and each engineer's machine supplies the value:

// .mcp.json, committed. Holds no token.
{
  "mcpServers": {
    "gitlab": {
      "command": "npx",
      "args": ["-y", "gitlab-mcp-server"],
      "env": { "GITLAB_TOKEN": "${GITLAB_TOKEN}" }
    }
  }
}

Made-up server name, for illustration. The ${VAR} syntax is from the Claude Code MCP docs.

Ask "who needs the server?", not "who owns the token?". If the whole team needs it, it goes in .mcp.json, with each token in a variable. That's Q40 (in full above). R09, also above, is the same idea from the other side: the shared file was already right, and only one machine was missing its variable.

Pull 2: "It's my version of a team thing." A personal variant of a team skill goes in ~/.claude/skills/ under a different name. The name matters. When a personal skill and a project skill share a name, the docs say the personal one runs. Keep the name /incident-summary and the team version stops running in your sessions. Name it /incident-summary-terse and you have both.

CLAUDE.local.md isn't a home for a skill variant. It's instructions, and it loads in every session you start in this repo. "Write incident summaries tersely" there would change every summary you get, including the runs that need the team's full style. That was Q19, above.

3 · The exception, kept for last: things that shouldn't be stored at all

Everything on the map loads again and again, at the start of sessions or whenever a skill is invoked. Some context is for one task: one log file, one investigation. That goes in no box. Type @path/to/file in your prompt, and Claude Code adds the file's content to this conversation. Nothing is saved for later sessions or for teammates. So add a zeroth question: is this needed again, or just now? Just now → @ in the prompt.

The mock question where this cost you a point:

Representative mock, 19 Oct, Q18

To debug one routing outage, a developer added the line '@logs/outage-0412.log' to the repository's root CLAUDE.md and committed it. The log is 900 lines and matters only for that single investigation, and the developer also works in 3 other repositories. A week later every teammate's sessions still load it at startup. What should the developer have done?

✗ Your pick: CCreate a .claude/rules/outage.md file with a paths glob of logs/** that holds the import line
✓ Correct: DReference @logs/outage-0412.log in the debugging session's prompt and leave CLAUDE.md alone
The other two options (A, B)
  • APut the import in the developer's ~/.claude/CLAUDE.md, out of the teammates' sessions
  • BPaste a prose summary of the log's key errors into the root CLAUDE.md under an Outage heading
Where it went wrong: C is a standing setup, just like the original line in CLAUDE.md: both load again and again. The log matters for one investigation, so it belongs in that session's prompt as @logs/outage-0412.log, and nowhere on the map.
