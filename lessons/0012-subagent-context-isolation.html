Subagent context isolation

The subagent's window is sealed. Only two things cross it: the task message going in, and the summary coming out.

On the real exam, objective 15 scored 0% on the score report, and objective 13 scored 50%. Three of the guide's techniques help keep a long exploration inside the context window: subagents and scratchpad files (task statement 5.4), and reading only what a search points to (2.5). This lesson covers subagents, and it follows the first video of Anthropic's Introduction to subagents course: What are subagents? (2:48).

A subagent knows only what you hand it, and you get back only what it chooses to report. Everything else is thrown away. The exam questions on this topic are really about those two hand-offs.

1 · The problem: everything stays in one window

In a normal Claude Code session, every tool call and every tool result is stored in the main context window (video). The video's example: you only want to know which service handles refunds. To find out, Claude reads 15 files, runs several searches and traces several function calls. All of that stays in your window, even though you needed a single fact.

That isn't only a cost problem. The exam guide names the symptom of a full window: in long sessions the model begins to answer inconsistently and to lean on generic "typical patterns" instead of the specific classes it found earlier (guide, task 5.4). If a stem describes that symptom, the question is about context management, not about the model's ability.

2 · The mechanism: one sealed window, two crossings

The video says the subagent gets two inputs: a custom system prompt from its configuration file, and a task description that the parent agent writes for it. It works on its own. Its file reads, edits and tool calls never show up in the main conversation. Then "the entire sub-agent conversation then gets completely discarded" (video).

The docs list exactly what a fresh (non-fork) subagent starts with (docs):

Gets at startup

  • Its own system prompt (not Claude Code's)
  • The task message the parent writes
  • Your CLAUDE.md files (Explore and Plan skip these)
  • A git status snapshot (Explore and Plan skip it)
  • Skills named in its skills field

Does not get

  • Your conversation history
  • Files the parent has already read
  • Skills already invoked in the session
  • Anything the parent worked out but didn't write into the task message

One exception: a fork inherits the parent conversation instead of starting fresh (docs). Unless a stem says fork, assume a fresh subagent.

3 · Two consequences the exam tests

The way in: the task message must carry everything. The guide's point is that a subagent only knows what its prompt tells it: nothing carries over automatically from the parent, and no memory is shared between invocations (guide, task 1.3). If a coordinator found something important in turn 30 and the task message says "write tests for the thing we found", the subagent has nothing to go on. The fix is to put the findings themselves into the task message. Telling the subagent to "remember" or to "check with the coordinator" doesn't work.

The way out: the summary is all you keep. The video names the cost: "the main window loses visibility into how the sub-agent reaches its conclusions". If the summary says "refunds are handled by the payments service" and you later need the exact handler, the file path and line went away with the subagent's window. So ask for the summary's shape in the task message: paths, line references, sources, dates. Task 5.1 of the guide asks for the same thing: subagents should attach metadata (dates, source locations, methodological context) to their structured outputs.

Trap: an option that "passes the full transcript back" or "lets the subagent see the whole conversation" sounds thorough, but it defeats the purpose of using a subagent. The verbose material is exactly what you were keeping out. The right fix is almost always to make one of the two crossings carry more structured information, not to open the window.

5 · When not to use one

The docs list when the main conversation is the better choice (docs):

Stay in the main conversation when…Use a subagent when…
the task needs frequent back-and-forth or iterative refinementthe task produces verbose output you won't need again
several phases share a lot of context (plan → build → test)you want to enforce tool restrictions or permissions
it's a quick, targeted change, or latency matters (a fresh subagent has to gather context from scratch)the work is self-contained and can come back as a summary

A subagent adds a hand-off and you lose sight of how it worked. Use one only when keeping its output out of your window is worth that.

6 · The three context strategies

These three techniques from the guide work together. This lesson covered the first. The next lesson goes deeper on the second.
