Show, don't re-describe

When Claude reads your rule differently each time, more words won't fix it. A couple of examples will.

You give Claude a rule in words, and sometimes it reads that rule differently from one run to the next. The fix isn't more words. It's two or three examples with the answer written next to them. This lesson shows that one move twice: before Claude writes anything, and after it gets something wrong.

Words leave gaps, and Claude fills each gap with a guess. An example is a gap with the answer already filled in, so put your examples exactly where Claude would otherwise guess.

1 · A rule with gaps

Prompt: "Reformat each customer name as Last, First."

That sentence seems clear until a name doesn't fit the pattern you pictured. Here are four names and three plausible ways Claude could read the rule (made-up readings, to show the idea):

Shaded = the runs disagree. The rule isn't wrong. It just leaves three gaps, and each run fills them its own way.

You could try to close the gaps with more words: "keep middle names with the first name, keep particles like van with the surname, leave single names alone…" Every one of those phrases has gaps of its own, though, and you have to predict every awkward name in advance.

2 · Fill each gap with one example

An example can't be read two ways. It's one real case with the answer already written down. Put one example on each gap and nothing is left to guess:

middle name?
↓

↓

↓

The exam guide treats concrete input/output examples as the best way to convey an expected transformation when prose descriptions keep being read differently, and says to give 2–3 of them (guide §3.5). Anthropic's prompting docs add that examples should be relevant, varied enough to cover the edge cases, and wrapped in <example> tags so Claude doesn't mistake them for instructions (prompting best practices).

Where the examples go matters most. Look at the John Smith row again: every run already gets it right, so an example there teaches Claude nothing. Ten names like John Smith tell it no more than one. Choose the inputs where the runs disagree.

3 · The same move, after something breaks

Now Claude has written something and got it wrong. Say a migration script turns a null discount into 0. Don't tell it "be careful with nulls". Give it the bug as three facts:

✓ A useful message fills all three boxes

INPUT{ id: 7, discount: null }
SHOULD BEdiscount = NULL
ACTUALLY ISdiscount = 0

✗ "Be careful with nulls" fills none of them

which row?
what's right?
what went wrong?

That's an example again, this time pointed at a failure. The guide describes this skill as supplying test cases that pair a concrete input with the output you expect, as a way to repair edge-case behaviour (for instance null values in migration scripts) (guide §3.5).

It's also why test-driven iteration works. A failing test already has those three boxes filled in, so pasting the failure tells Claude exactly what to fix. Claude Code's docs give the same advice: instead of "implement a function that validates email addresses", list test cases like user@example.com → true and user@.com → false, then ask Claude to run them (Claude Code best practices).

4 · When examples are not the fix

Examples fix one kind of problem. The exam builds its distractors from the other two:

The usual distractor: "rewrite the instructions in more detail." That's the prose that already failed, only longer. And in sample Q2, "add 5–8 routing examples" is wrong because examples cost extra tokens and leave the real problem untouched (guide).
