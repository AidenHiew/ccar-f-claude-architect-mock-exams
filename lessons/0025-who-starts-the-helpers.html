Who starts the helpers, and who notices when it stops?

On the 21 October practice paper, two questions were lost on words, not on thinking: your instinct matched the correct answer, but one key word in the right option was new to you. This lesson teaches those words and a few close relatives.

The plain question. When an agent hands work to helper agents, how does it start them? And when the agent stops working for any reason, whose code notices?

An everyday example: a restaurant kitchen.

  • The head chef hands out tickets. Each ticket tells one cook what to make. The cook never heard the customer, so the ticket has to say everything the cook needs.
  • One ticket at a time is slow. If the chef hands out a ticket, waits for that dish, then hands out the next, three dishes take three times as long. Hand out all three tickets at once and three cooks work side by side.
  • The manager stands outside the kitchen. The manager doesn't cook. The manager's job is to check every table got its food. If the chef faints, the power cuts out or the oven catches fire, the cause doesn't matter: the manager goes to the table with a note of what was ordered and what happened.

An agent system has the same three parts. The head chef is the coordinator (the main agent). A ticket is a Task call, which starts a subagent (a helper agent). The manager is the wrapper: your own code outside the agent.

A Task call is how a coordinator starts a subagent. Several Task calls in one response run at the same time.
A wrapper is your own code around the agent loop (the code that keeps the agent calling Claude and its tools, explained in section 2). It checks how the loop ended, and for any bad ending it hands the case to a human.

Where this cost you points. Both questions are shown in full, as you saw them, with your pick and the correct answer. Words you'll meet in them:

  • Tool names written like set_payment_plan or escalate_to_human are tools the agent in that scenario can call. A tool's client code is the code that runs when the agent calls it.
  • An MCP server is the program that provides tools to an agent.
  • An isError result is a tool reply that reports a failure as an ordinary result the model can read, instead of crashing. A retryable flag on it says whether trying again might work.
  • A system prompt is the standing instructions an agent gets at the start of every session.
  • A coordinator is the main agent that hands out work; a Task call and a subagent brief are explained in section 1.

1 · Starting subagents: the Task tool

A coordinator can't start a subagent by wanting to. It has to call a tool, the same way it calls a search tool or a database tool. That tool is the Task tool. One use of it is a Task call: "start a subagent, and here is its brief." (Newer Claude Code docs also list it under the name Agent; it is the same tool.)

Three facts about it that the exam tests:

  1. The coordinator must be allowed to use it. Every agent has an allowedTools list: the tools it may call. If "Task" isn't on the coordinator's list, it cannot start any subagent, whatever its prompt says. A question where "the coordinator never delegates" and the config lists allowedTools: ["WebSearch", "Read"] (a web search tool and a file-reading tool, but no Task) is pointing at this.
  2. The brief is all the subagent gets. A subagent does not see the coordinator's conversation. Anything it needs, such as earlier search results, must be written into the Task call's prompt. (That's the ticket in the kitchen example.)
  3. Several Task calls in one response run in parallel. This is question 9 of the paper, shown in full above.

AgentDefinition: the job description for one kind of subagent. The coordinator starts subagents; an AgentDefinition says what each kind of subagent is. It holds three things: a description (what this subagent is for), a system prompt (its standing instructions), and its tool restrictions (which tools it may use). So "the search subagent must only search, never write files" is set in the search subagent's AgentDefinition, not in a prompt line asking it to behave.

2 · The wrapper: your code around the loop

First, the loop itself. An agent loop is the code that keeps the agent working. It sends the conversation to Claude and reads the stop_reason on the reply (a field that says why Claude stopped writing):

  • "tool_use": Claude wants a tool. Run it, add the result to the conversation, and send it back for the next step.
  • "end_turn": Claude has finished. Show the answer and stop.

That loop only works while it is running. If a tool's code throws an error nobody catches, or the hosting platform kills the session, the loop is gone. The loop can't escalate, and neither can the model. Something outside the loop has to notice. That something is the wrapper.

Wrapper Your code. It starts the loop, then checks how the loop ended.
Agent loop Send to Claude → read stop_reason → run tools → repeat until "end_turn".
Tools set_payment_plan, search, and so on.
  • Normal ending ("end_turn"): nothing to do.
  • Any bad ending (an uncaught error, the session killed, anything else): open a human case with the account ID, the issue and the last step reached.

That's why B beats D in the paper's question 4. D makes one tool's failures safer. That's a real improvement, but it covers one of the two causes. The 120-second kill never touches set_payment_plan, so it still ends sessions with nobody told. The wrapper doesn't care which cause it was. It only asks "did the loop end normally?"

The handoff note matters too. The staff taking the call can't see the chat transcript. So the case must carry the facts: who the customer is, what went wrong, and what was in progress. The exam guide calls this a structured handoff.

Same thing, other names. The exam guide doesn't give this layer a name of its own. Questions may call it a wrapper, the orchestration layer, an outer loop or supervisor code. All four mean code outside the agent loop. The wrapper is not the loop; it is the code that runs the loop and watches it.

3 · Coming back to a session: --resume and fork_session

A session is one saved conversation with the agent, including the files it read and what it found. Two words for reusing one:

WordWhat it doesUse it when
--resume <session-name>Continues one named earlier session, picking up where it left off.You want to carry on the same piece of work. Most of what it found is still true. Everything you try next goes into that same conversation.
fork_sessionMakes a separate copy (a branch) of a session. Each copy goes its own way; the original is untouched.You want to try two different approaches starting from the same analysis, without one affecting the other.

One more rule: stale results. If files have changed since the session read them, its old tool results are out of date. If only a few files changed, resume and tell the agent exactly which files changed, so it re-reads just those. If most of what it read is out of date, start a new session and give it a short written summary of what's still true. That is more reliable than resuming with stale results.
