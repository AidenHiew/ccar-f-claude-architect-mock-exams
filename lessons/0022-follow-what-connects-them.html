Follow what connects them, not how many

You've practised these two topics more than any other weak row, and they're still weak. Your misses show why: each pick chose an amount, and each correct answer followed a connection.

When Claude faces many things at once (many files to read, many bugs to hand back), ask one plain question: what connects them?
The right option follows that connection. "How many at a time" isn't the decision. It comes out of the answer.

An everyday example. There's a water stain on your ceiling.

  • The right move: start at the stain and follow the pipe back until you reach the joint that's leaking. You open only the bits of wall the pipe runs through.
  • Tempting move 1: open every wall in the house. You'll find the leak eventually, but you've wrecked the place doing it.
  • Tempting move 2: look closely at the stain and nothing else. It's quick and tidy, but the cause isn't there.

The plumber then finds three problems: the leaking joint, a rotten board that the leak has been dripping on, and a squeaky door in another room. The joint and the board go in one job, because fixing the joint changes what happens to the board. The door is a separate job. Whether they share a room doesn't matter. The pipe is what connects them.

Where this has cost you points. Five questions, in full, in the order you answered them, with your pick and the correct answer.

Exam-style drill, 8 Oct, Scenario 6 (3.5)

(Scenario 6) Dates arrive in six formats. After each run the developer says "the dates are still wrong, fix it." Each round fixes some formats and breaks others; five rounds, no improvement. What next?

✗ Your pick: BFix one failing document per round so each change is easy to review
✓ Correct: CSend all failing cases at once, each with input and expected output
The other two options (A, D)
  • AAsk Claude to rewrite the whole prompt with much more emphasis on dates
  • DAdd "be very careful with date formats" in capitals to the prompt
Where it went wrong: B sets the amount to one: one document per round, small and easy to review. But the stem says the formats are connected: fixing one breaks another. Claude can't keep a format working that it never sees, so the key sends every failing case at once, each with its input and expected output.

D3 quiz, 16 Oct, Q10 (3.5)

Reviewing Claude's rewrite of a CSV importer, you find three problems. Dates are parsed in UTC instead of the account's timezone. The dedup key is built from the parsed date, and so late-evening rows collide with the next day's rows. Rows with a null email are also dropped by the dedup step. How should you hand these back?

✗ Your pick: COpen three separate sessions, one per problem, and then merge the three diffs together
✓ Correct: BDescribe all three in one message, explaining how the date bug feeds the dedup key
The other two options (A, D)
  • AFix the timezone bug first and raise the dedup problems after that change is verified
  • DAsk for a fresh rewrite of the importer, noting that dates and nulls need extra care
Where it went wrong: C splits the work three ways, one session each. The stem names the connection: the date feeds the dedup key, and the null rule lives in that same dedup step. Three sessions each fix their piece without seeing the others. The key keeps them in one message and says how they connect.

✗ Your pick: BBoth bugs are in the same repository and were logged the same day
✓ Correct: DThe second bug reads the value that the first bug calculates wrongly
The other two options (A, C)

Representative mock, 19 Oct, Q26 (3.5)

Claude is rewriting the function that rounds route distances for driver pay. Over 4 rounds of chat feedback, each fix breaks a case fixed earlier: one round broke zero-length legs, another broke distances near the 0.5 km boundary. The team knows the expected output for 15 such cases. What should the developer do?

✗ Your pick: BDescribe the 15 cases in one long prose message and ask Claude to handle them together
✓ Correct: AWrite tests for the 15 cases first, then iterate by giving Claude the failing tests
The other two options (C, D)
  • CFix the rounding by hand and ask Claude only to tidy the code style around the function
  • DGive Claude 2 input and output pairs for the hardest cases and go on as before
Where it went wrong: B gets the amount right (all 15 at once) but in a form that is told once and never checked again. What connects the rounds is the set of cases that must keep passing. Tests hold that set and re-check every case on every round, so a re-broken case shows up straight away.

Representative mock, 19 Oct, Q43 (2.5)

An engineer asks how a booking cancellation flows from the API to the refund. The agent's first move was to Read all 220 files under app/, and by file 140 its context was full and its answers became vague. The cancel endpoint is a single controller action. How should the agent explore instead?

✗ Your pick: BSpawn a subagent to Read all 220 files and return one summary of the whole app
✓ Correct: CGrep for the cancel action's route or method name, Read that action, then follow its calls
The other two options (A, D)
  • ARead the 220 files in batches of 40 and summarise each batch before the next one
  • DGlob app/**/*.rb, then Read the files whose names suggest a cancellation, refund or booking
Where it went wrong: B still reads all 220 files; it just does the reading in a subagent. The stem hands you the starting point: one controller action. The key finds it with Grep, reads it, and follows its calls to the refund. You read only the files the flow actually passes through.

1 · Your picks swing; the keys don't

Put your five picks on a line from "a little at a time" to "everything at once". The 3.5 picks moved from one end to the other: split twice, then bundle twice. The 2.5 pick sits at the far end. The correct answers aren't on this line at all. Each one follows something the stem names.

What each correct answer followed

This is why practice hasn't stuck. Each lesson gave you a correct rule ("send them together", "don't read everything"), and the next question that looked similar got the rule as an amount. The fix isn't another amount rule. It's a habit: before the options, find the words in the stem that say what connects to what.

2 · In 2.5, the connection is how the code links up

A few plain words first. A caller is code that runs a function. An entry point is where a flow starts, such as the handler for a route. A base class is shared code that other classes build on (they extend it), and each of them can replace one of its methods with their own version (they override it).

Every 2.5 skill in the exam guide has the same shape: find one known starting point, then follow its links. The guide's own wording, with the link each one follows:

What the guide says to doThe link you followWhat the distractors do instead
Start with Grep for entry points, then Read to follow imports and trace flows, instead of reading every file firstThe calls and imports out of the entry pointRead everything (in one go, in batches or in a subagent); read files whose names look right
Trace a function across wrapper modules: list all its exported names first, then search for each oneEvery name the function goes bySearch only the original name; read every file that imports the module
Grep: search inside file contents for things such as function names, error messages or import statementsA name or string inside filesGlob, which only sees file names and paths
Glob for "finding files by name or extension patterns", e.g. **/*.test.tsxWhere files are and what they're calledGrep for a word, which also hits every file that merely mentions it

One more 2.5 fact, which isn't about links but is in the guide: Edit changes a file by matching a piece of unique text. When Edit fails because that text appears more than once, the fallback is Read to load the whole file, then Write to save it back with the change.

3 · In 3.5, the connection is between problems, or between rounds

Refinement asks two kinds of "what connects them?"

Between problems: does fixing one change another? If one bug's output is another's input, or they're handled in the same step, they go in one detailed message that says how they connect. If not, they go one at a time, each fix checked before the next. Same file, same reviewer, same day or same log isn't a connection.

Between rounds: what has to stay true from one round to the next? That decides the form of your feedback:

What the stem saysThe move (guide 3.5)
Prose instructions get a different result each run2–3 concrete input/output examples
Fixes keep re-breaking cases, and you know what each case should outputWrite the tests first, then iterate by sharing the failing tests
One kind of input fails (the guide's example: null values in a migration script)That input and its expected output, as a specific test case
Unfamiliar domain; you don't yet know which questions matterThe interview pattern: Claude asks you questions before it implements

Notice that none of these rows says "one" or "all". Each says what Claude needs to keep in view. The amount follows.

4 · The check, for exam day

  1. Before you read the options, underline the words that link things: calls, imports, re-exports, extends, is built from, reads the value, breaks a case fixed earlier, knows the expected output.
  2. Pick the option that follows those words.
  3. Be suspicious of an option whose only selling point is an amount: everything at once, one at a time, in batches, only the lines that match. And of one that groups by closeness: same file, same folder, same day.
