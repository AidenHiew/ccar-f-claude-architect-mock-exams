Use the switch Claude Code already has

Four of your misses on skills and rules have the same shape: Claude Code already had a setting for the job, and the pick built something by hand instead.

Before you pick, ask one plain question: does Claude Code already have a setting that does exactly this?
If it does, that setting is the answer. A skill plus a hook, a line asking Claude to behave, or a clean-up step afterwards are all ways of rebuilding it by hand, and they lose to the setting.

An everyday example. You want your phone to go silent at 10 pm every night.

  • The right move: turn on the phone's built-in quiet-hours schedule. Set it once. It works every night, whether you remember or not.
  • Tempting move 1: a sticky note on the mirror saying "mute your phone". That works until the night you forget.
  • Tempting move 2: install an app that watches the clock and mutes the phone at 10. That works too, but now you're keeping an app running to do what one switch already does.

The sticky note is "tell Claude to…". The clock-watching app is "a skill plus a hook". The quiet-hours switch is the setting Claude Code ships with.

Where this has cost you points. Four questions, in full, with your pick and the correct answer.

D3 quiz, 16 Oct, Q6

Your TypeScript repo keeps tests next to the code they cover, as *.test.ts files across about 60 directories. The 300 lines of testing conventions sit in the root CLAUDE.md. They load in every session, including infra-only work, and adding them to new directories keeps getting missed. What is the best place for them?

✗ Your pick: DA testing skill, plus a hook that invokes it whenever Claude opens any file ending in .test.ts
✓ Correct: BA .claude/rules/ file with paths frontmatter set to **/*.test.ts, loaded when tests are edited
The other two options (A, C)
  • AA CLAUDE.md in each directory that holds tests, every one carrying the same testing conventions
  • CThe root CLAUDE.md under a Testing heading that tells Claude to apply it only to test files
Where it went wrong: D would work, but it rebuilds by hand something Claude Code already does. A .claude/rules/ file with paths: **/*.test.ts loads on its own when Claude reads or edits a test file, in any of the 60 directories, and stays out of every other session. No skill to write, no hook to keep working.

✗ Your pick: AAdd a line to SKILL.md telling Claude to keep its final report under 500 words
✓ Correct: CSet context: fork in the skill's frontmatter to run it in an isolated sub-agent
The other two options (B, D)
  • BRestrict allowed-tools in the skill's frontmatter to the Read and Grep tools only

Where it went wrong: A shortens the last 500 words. The 30,000 tokens are the working-out before the report: every manifest it read. Only one switch keeps that working-out out of your chat: context: fork runs the skill in its own subagent, and only the result comes back.

Every pick here could work some of the time. Each one rebuilds, by hand or by instruction, something a single setting already does every time.

2 · How the two you missed most actually work

context: fork. When a skill has this setting, Claude Code starts a separate subagent and gives it the skill's instructions as its task. The subagent does all the reading in its own context. Only its result comes back to your conversation. The docs add one detail worth knowing: the subagent doesn't see your conversation history, so the skill's instructions have to stand on their own.

Without fork (your pick A on Q4)

Your conversation
↓ /analyze-deps runs here
Dozens of manifests read: ~30,000 tokens
500-word report

All 30,000 stay in your chat. A shorter report trims only the last box.

With context: fork (correct)

Your conversation
Subagent: reads the manifests in its own context
↓ only the result returns
Final summary

The working-out stays in the subagent. Your chat gets the summary.

The guide gives two kinds of skill that want this: ones with verbose output (codebase analysis, like Q4) and ones with exploratory context (brainstorming alternatives).

Two skills with the same name. Claude Code doesn't load both and choose. It has a fixed order: personal beats project (and an organisation's managed skills beat both). So:

SetupIn this engineer's sessionsIn teammates' sessions
Copy in ~/.claude/skills/release/, same name as the team's release/release runs the personal copy. The team's version is hidden from them.Unchanged: the team's version.
Copy in ~/.claude/skills/release-strict/, new nameBoth: /release and /release-strict.Unchanged: the team's version.

That's why the guide says personal variants get a different name: with the same name, you lose your own access to the team version.

Path rules, one more time. A file in .claude/rules/ with a paths field loads when Claude uses Read, Write or Edit on a file matching the glob (or reads one with cat or head). A rule with no paths field loads in every session, like CLAUDE.md. The guide's reason to prefer a glob over a CLAUDE.md in each folder: **/*.test.ts follows test files into all 60 directories, including ones created next month.

3 · One trap in the other direction

"Use the built-in switch" doesn't mean "pick any switch name you recognise". Check that the switch does this job:

  • context: fork separates the conversation. It doesn't restrict tools by itself; the subagent type decides those. (The 19 Oct mock had this in Q20: a skill that already used context: fork still force-pushed a branch.)
  • A rule with paths loads on file access. For a runbook someone starts by choice, like a database failover, a skill fits better, because nobody's editing a matching file when the failover starts.
  • Answers sometimes name a setting that doesn't exist, such as context: isolate. If you don't recognise it from the guide, be suspicious.
Heads-up on allowed-tools. The exam guide says allowed-tools in skill frontmatter restricts which tools the skill can use. Today's Claude Code docs describe it differently: it pre-approves the listed tools for that turn without taking others away, and a separate field, disallowed-tools, does the removing. The exam is written from the guide, so on the exam treat allowed-tools as the way to limit a skill's tools. This lesson's quiz doesn't test it.
