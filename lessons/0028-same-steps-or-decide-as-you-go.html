Same steps every time, or decide as you go?

On two practice papers, Representative Mock 3 (a full 60-question mock, 23 October) and weak-topics paper 3 (a paper on your weakest topics, 24 October), you lost 7 questions. This page shows all 7 in full, plus one you got right. Part 1 has 2 about splitting a big job into steps. Part 2 has 3 where you picked plan mode and something else was the fix (one of them is also a splitting question). Part 3 has 2 about when an agent's loop should stop. You don't need to remember any of them.

Four topic numbers from the exam guide (the official guide that lists what the exam tests) come up on this page: 1.6 is splitting a big job into steps, 3.4 is when to use plan mode, 3.5 is improving Claude's output round by round (by showing it examples, or by writing tests and sharing what fails), and 1.1 is how an agent's loop decides to stop. One more, 4.2 (giving the model examples in the prompt), comes up once as a wrong pick. On the real exam in September, the 1.6 objective on splitting work as you go scored 50%, and stopping a loop safely scored 0%. The page is in three parts.

The plain question. A job is too big to do in one go. Do you fix the steps in advance, or let what you find decide the next step?

An everyday example. A landlord checks 20 flats every spring. Each flat gets the same 3 checks: smoke alarm, boiler, damp. What one flat shows doesn't change what gets checked in the next. So it's a fixed list, flat by flat, and at the end one walk round the whole building for things that cross flats, like a shared roof leak.

Now one tenant reports water coming through the ceiling. Nobody knows where it starts. The plumber looks at the flat above, finds a wet pipe, follows it to the roof, and finds the gutter. Each finding decides where to look next. No list written at breakfast could have said "gutter".

And if the job is big and nobody knows how it fits together, like re-wiring an old building with no drawings, you do a bit, learn, and re-plan. You start with the circuits most rooms use, and you change the plan when you find something.

The one idea: read the stem for how much is known up front. Same steps every time → a fixed chain. What you find decides the next step → let the agent choose its next step from each finding. Nobody knows how it fits and surprises turn up partway → do the most-used parts first and re-plan after each batch. Plan mode is a different tool (Part 2): it plans how to build a big change before editing, and it never checks the results.

Words to start with

Stem
The question's own text, above the four options.
Prompt
The written instructions given to the model for a task.
Decomposition
Splitting a job into smaller steps. "Which decomposition fits?" means "which way of splitting this job fits?"
Fixed chain (the exam guide says "prompt chaining")
A job split into steps decided in advance, always in the same order. Each step is its own prompt, and the next step works from the last one's output. Example: summarise, then mark, then write.
Dynamic subtasks (the guide says "dynamic decomposition")
The agent decides its next step from what it has just found. The steps are not known in advance.
Coordinator
The main agent that hands out jobs (subtasks) to helper agents and collects their results.
Re-plan after each batch (adaptive re-planning)
Do a chunk of the work, look at what it showed, then change the order of what's left before doing the next chunk.
Attention spread thin (the guide says "attention dilution")
When one pass covers too much, the model looks closely at the first few items and skims the rest. The fix is a pass per item, then one pass across all items for problems that span more than one.
Plan mode
A Claude Code mode where Claude explores the code and writes a plan, and makes no edits until you approve the plan. The guide says it is for big changes: many files, more than one valid approach, or design decisions.
Direct execution
Just making the change, without plan mode. For small, clear changes.
Tests first, share the failures
Write a set of automatic checks (a test suite) for what the code must do before asking Claude to change it. Then run them on each new version and paste the ones that fail back to Claude, until all pass.
Edge case
An unusual input that code must still handle, such as a public holiday or an empty list.
Agent loop, tool call
An agent runs in a loop: send the conversation to Claude, get a reply, and if the reply asks for a tool (a function such as "search the logs"), run it, add the result, and go round again. Each run of a tool is a tool call.
stop_reason
A field on every reply from Claude that says why it stopped writing. "tool_use" means "run the tool I asked for and send me the result". "end_turn" means "I'm finished".
Cap
A maximum number of loop rounds or tool calls, after which the loop is stopped no matter what.

Words that appear in the past questions (you don't need these to follow the lesson, only to read the questions):

  • Module: one file or unit of code. Perl is a programming language.
  • SQL injection: a security hole where text typed by a user gets run as a database command.
  • Pull request: a proposed code change that colleagues review. To refactor is to rewrite code without changing what it does.
  • Null handling, time-zone conversion, lock ordering: three kinds of bug a code review looks for: empty values, wrong times across time zones, and two parts of a program waiting on each other forever.
  • Utility: a small shared piece of code that many other parts use. Legacy code is old code nobody fully understands any more.
  • Subagent: a helper agent that does one job for the main agent and reports back.
  • JSON: a structured text format that programs read. In the parking question, "2P" on a sign means "2-hour parking".
  • Content array, text block: a reply from Claude is a list (the content array) of pieces called blocks. A text block is a piece of writing; a tool-use block is a request to run a tool. One reply can hold both.
  • "max_tokens": another stop_reason value. It means the reply was cut off because it hit a length limit, not that Claude is finished, so it isn't a signal to stop the loop either.
  • Iteration: one round of the loop. ms: milliseconds (1,000 ms = 1 second). On-call: the engineer on duty to handle problems. In production: in the live system, used by real customers.

A plan, but one that changes after each batch.

For a fixed chain that reviews many files, the usual shape is one pass per file, then one pass across all files. When a single pass over many files gives detailed comments on the first few and thin ones later, that's attention spread thin: give each file its own pass. Then, because some bugs span two files (a change in one breaks a caller in another), add one pass that looks across all of them. If nothing can cross from one item to another, the per-item passes are enough. Here is the question where you got this right:

Part 2 · Plan mode plans how to build. It never checks results.

Plan mode has pulled you off the right answer 3 times in 2 papers. Each time it looked sensible, because planning sounds careful. But it does one specific job. Plan mode is a 3.4 answer: Claude explores the code and plans how to make a big change before editing anything, when there are many files, more than one way to do it, or a design choice. The guide's examples are moving a library used by 45+ files, or splitting a big app into services.

What plan mode never does:

  • It never runs the code or checks whether results are right.
  • It doesn't fix output that comes out different each time. If Claude misreads what you want, the plan is written from the same misreading.
  • It doesn't handle surprises found partway through the work. That is 1.6: a plan that changes after each batch. Using plan mode at the very start, to map the code, is fine. What fails is a plan that is never changed when surprises turn up.
What is broken (from the stem)TopicThe fix
A big change hasn't started yet: many files, more than one valid approach, a design choice.3.4Plan mode, then carry out the plan.
Claude keeps misreading what output you want; written corrections fix one case and break another.3.52–3 inputs, each with the exact output it should become.
Many edge cases or a speed target, and a past version broke something nobody noticed.3.5Write the tests first, then share the failures with Claude each round.
Nobody knows how it fits; something important turned up partway.1.6Most-used parts first, re-plan after each batch.

Part 3 · A cap never replaces stop_reason

Two short rules for an agent's loop. stop_reason decides when the loop ends: run the tool on "tool_use", finish on "end_turn". Text in the reply means nothing on its own, because one reply can hold a sentence and a tool request. A cap is only a safety net: set it well above a normal run, so it only stops runaways (runs stuck repeating themselves), and tell a person when it is reached. The exam guide names three things not to use to end the loop: reading the reply's wording ("I'm done"), a cap as the main way of stopping, and "the reply contains text".

Weak-topics paper 3, 24 Oct, question 5

The incident agent's loop already runs tools on stop_reason "tool_use" and ends on "end_turn". Last week one run hit a corrupted log file and called search_logs with the same query 312 times before an engineer stopped it, at a cost of about $90. Normal investigations take 25 to 30 tool calls. The team wants protection against runaway runs that does not cut normal investigations short. What should you add?

✗ Your pick: BReplace the stop_reason check with a cap of 30 tool calls on each run
✓ Correct: AKeep stop_reason as the signal and add a 60-call cap that alerts on-call
The other two options (C, D)
  • CEnd a run when Claude's reply says it is unable to make more progress
  • DAdd a prompt line telling Claude not to repeat a search it has already run
Where it went wrong:
  • The deciding word in your pick is Replace. stop_reason is how the loop knows Claude is finished. A cap doesn't know that; it only counts. So a cap can never replace stop_reason.
  • Your pick also sets the cap at 30, and normal runs take 25 to 30 calls. Some normal investigations would be cut off right at the end, which the stem rules out.
  • A keeps stop_reason as the signal and adds a cap well above normal (60) as a safety net. Normal runs never reach it; a runaway like the 312-call one stops at 60 and a person is told.
  • Even a 60-call cap would be wrong if it replaced stop_reason. The rule: stop_reason decides when the loop ends; a cap only catches runaways.
