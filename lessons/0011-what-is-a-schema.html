What a schema is, and what it can't promise

Objective 22 scored 67% and objective 24 scored 50%. Both depend on this one idea.

When an application asks for "a JSON record for an invoice", there are many valid ways to write one. Your code can only read one of them. A schema is a written description of that one shape: which fields must be present, what type each value is, and which values are allowed. JSON Schema describes itself as "a declarative format for describing the structure of other data". A schema is data, not a program, and it's written in JSON itself.

Data either validates against a schema (it fits the shape) or it doesn't. That pass-or-fail check is the whole point. Your downstream code can then rely on the shape without checking it again.

A schema is a contract about shape. It can guarantee that a field exists and is a number. It can't guarantee that the number is true.

Reading one, keyword by keyword

Here is an invoice-extraction schema. Each keyword shown is in the exam guide's JSON Schema list (guide, technologies appendix), which covers required and optional fields, enums, nullable fields, and an "other" value paired with a detail string.

{
  "type": "object",                        ← the output is one JSON object
  "properties": {                          ← the fields it may contain
    "invoice_number": { "type": "string" },
    "total":          { "type": "number" },  ← "42.50" (a string) fails, 42.5 passes
    "due_date":       { "type": ["string", "null"] },  ← nullable: null is a legal answer
    "doc_type": {
      "type": "string",
      "enum": ["invoice", "credit_note", "other", "unclear"]  ← only these values
    },
    "doc_type_detail": { "type": ["string", "null"] }  ← says what "other" means
  },
  "required": ["invoice_number", "total", "due_date", "doc_type", "doc_type_detail"],
  "additionalProperties": false            ← no fields beyond the list
}

Note that due_date is in required and nullable. "Required" means the key must appear. Nullable means its value may be null. Together they say: always tell me about the due date, and if there isn't one, say so with null. The type-array syntax ["string", "null"] appears in Anthropic's structured-outputs docs, and additionalProperties "must be set to false for objects" there.

Enforcement works by constrained decoding: the schema is compiled into a grammar, and Claude can only produce tokens that keep the output valid. That's why the docs can say "No more JSON.parse() errors". The guide (v0.2) frames the same idea as tool use with a schema being "the most reliable approach for guaranteed schema-compliant structured output" (4.3).

What a schema can't do

JSON Schema's own docs explain the limit. Because a schema can't contain code, there are "constraints on the relationships between data elements that can't be expressed", so real validation has two phases: structural, then semantic. The guide tests exactly this split (4.3, 4.4):

The fabrication trap

Suppose due_date were {"type": "string"} and required, and a document has no due date. Constrained decoding forces a string to appear, so the only valid outputs are invented dates. The schema left Claude no truthful answer. The guide's fix is to make a field optional (nullable) whenever the source documents might lack that information, so the model isn't pushed into fabricating a value just to satisfy a required field (4.3).

Enums fail the same way. If doc_type allows only invoice and receipt, a credit note gets filed as one of them. Add "unclear" for ambiguous cases, and "other" plus a detail string for categories you didn't foresee (4.3).

Exam pattern. When a stem says extractions contain plausible but wrong values for data that is sometimes missing, the cause is the schema, not the prompt. "Tell the model not to guess" only makes guessing less likely. A nullable field, or an other/unclear enum value, gives Claude a legal way to tell the truth. This is the same reduce-versus-remove distinction from Lesson 5.
