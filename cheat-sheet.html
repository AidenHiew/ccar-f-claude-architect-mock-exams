Cheat sheet

Three options usually would work. The exam asks which one owns this problem, and the deciding fact is always in the question.

1 · Exam-day method

  1. Pass mark 720 on a 100–1,000 scale. There's no penalty for guessing, so answer every question. You get 4 scenarios, drawn at random from a pool of 6.
  2. Before the options, name the problem. Underline the deciding fact. That might be a number, something already tried ("a prompt line was added and barely helped"), or who or what is waiting on the result.
  3. List every requirement in the question (speed, cost, "every time", "the whole team"). Cross out any option that fails even one. Wrong options are built from the requirements you skip.
  4. The neighbour check. For your pick, ask: is this a real fix for a different problem? Many of your recent misses were exactly that (see the first card in Part 2).
  5. Guarantee or nudge? If the question needs something to happen every time, choose code, a hook or a setting over a prompt line. Prompts are probabilistic.
  6. Unsure? Pick your best option, flag the question and move on. Come back at the end.

2 · Your traps (from your own misses)

Each card is a pattern that cost you marks more than once. The green line is the rule that beats it.

The neighbouring fix
You picked a real fix from a different problem: plan mode on a testing question, routing to a person on a prompt question, or examples on a workflow question.
Ask: what exactly is missing here? Pick the option that supplies that, not the one that sounds most capable.
A test or check when the right outputs are known (3.5)
Example: Claude maps carrier tracking updates to 8 status codes. After 2 rounds of written corrections, every output is a valid code but 1 in 10 is the wrong one, and the developer knows the right code for each update. You picked "a test that checks each result is one of the 8 valid codes". It passes on the wrong ones.
A shape check passes wrong answers. Show Claude real inputs with their exact right outputs, for the inputs that are going wrong.
Lesson 30
Tests, interview or examples? (3.5)
The cases are known and listed, or there's a speed target → write tests first.
You know the right outputs, but words keep failing → input/output examples.
It's a new area and nobody knows the cases yet → have Claude interview you first.
Lesson 29
Plan mode as the answer to everything
Plan mode plans how to build a big change before any edits. It doesn't supply tests, examples or missing knowledge, and it doesn't set a fixed order of steps.
Plan mode is for a big multi-file change with several possible designs. It's not the fix for "outputs are wrong" or "we don't know the cases".
Lesson 28
Prompt question, answered with a person (4.2)
Example: a classifier prompt has 11 rules, consistency only rose from 68% to 71%, and the question asks what to add to the prompt. You picked "a step that sends each unclear item to a reviewer". You made this pick twice in a row.
If the question says "add to the prompt", an option that hands the decision to a person isn't a prompt change.
Rules or examples, in the wrong order (4.1 / 4.2)
No exact definition in the prompt yet → write it in first (what to flag, what to skip).
Rules already written and new cases still slip past → a few hard cases, each with the reason.
Examples of clear, easy cases teach nothing about where the line falls.
Lesson 27
The model's own confidence score
Options that have the model rate its own confidence or severity, then filter or route on that score. This cost you 4 questions on Mock 2.
For escalation or severity, a confidence score the model gives itself isn't reliable: use explicit criteria. Routing low-confidence fields to human review is right only when accuracy has been checked against labelled data for each document type and field (5.5).
Replacing the signal instead of adding a guard (1.1)
Example: an incident agent's normal runs take 25 to 30 tool calls, and one run repeated the same search 312 times. You picked "replace the stop_reason check with a cap of 30 tool calls", which cuts normal runs short. The key kept stop_reason and added a 60-call cap that alerts on-call.
Keep stop_reason as the loop's signal, and add a cap as a safety net that alerts or escalates.

Domain 1 · Agents and workflows

TopicAskThen
Loop control (1.1)ATTEMPT 1 · 50%What did stop_reason say?tool_use → run the tool, append the result, continue. end_turn → stop. A cap is a guard, not the signal.
Subagents (1.2 / 1.3)What does the subagent know, and what comes back?Only what you put in its prompt, since context isn't inherited. You get back only what it reports. A coordinator starts subagents with Task (it must be in allowedTools). Several Task calls in one response run in parallel.
Every session ends in a resolution or a hand-off (1.4)ATTEMPT 1 · 0%What if the agent loop (the code that keeps calling Claude and its tools) dies: an uncaught tool error, or the platform kills the session?The model can't escalate from a dead loop. Put a wrapper (your own code around the loop) that checks how the loop ended and hands any bad ending to a human.
Enforcement (1.4 / 1.5)Must it happen every time?Strongest to weakest: make the wrong thing impossible (a hook or gate), then run the real check before it happens, then detect it afterwards, then just tell the model not to. Hooks and gates guarantee; prompts nudge.
Escalation (5.2, often in agent scenarios)Is one of the three triggers present?The customer asks for a person (hand over immediately); a policy gap (the rules don't cover the request, or it needs an exception); or no progress (the agent can't move the case forward). Never escalate on emotion or self-rated confidence.
Fixed chain vs adaptive (1.6)ATTEMPT 1 · 50%How much is known up front?Same steps every time → a fixed chain (the same steps in the same order). Each finding decides the next step → let the agent choose. Unknown and full of surprises → do the most-used parts first and re-plan after each batch.
Two similar agents or workflowsWhat actually differs between them?Split off only the part that differs. Copying the whole thing and sharing the whole thing are both wrong.

Domain 4 · Prompts and structured output

Few-shot (4.2)ATTEMPT 1 · 50%Are rules written, and still inconsistent?Yes → 2–4 hard examples, each with the reasoning for why that call and not the alternatives. No → write the rules first. Examples go exactly where Claude would otherwise guess.

How they load

  • At launch: CLAUDE.md and CLAUDE.local.md in the current folder and every parent folder. They add together; one doesn't override another.
  • A CLAUDE.md in a sub-folder loads only when Claude reads files in that folder.
  • A rules file without paths: loads at launch, like CLAUDE.md. With paths: it loads when a matching file is read.
  • A file loads whole. A heading inside it ("for repo X only") doesn't limit where it loads.
  • The project-root CLAUDE.md survives /compact. Sub-folder CLAUDE.md files and path-scoped rules come back only when matching files are read again.

When two places clash

  • MCP: same server name in two places → local, then project, then user. The closest wins.
  • Rules: ~/.claude/rules/ loads before the project's rules, so the project wins.
  • Skill vs command with the same name → the skill wins.
  • CLAUDE.md is advice, not enforcement. A hard limit ("never touch prod") goes in permission deny rules in settings, or a hook.
  • Behaving differently for one person? Run /memory to see which files actually loaded.

4 · Hard facts

These follow the exam guide and the 2026-09 docs notes. Where the live docs differ (for example, forced tool_choice returning 400 on some new models), the exam still marks the guide's answer: tool_choice any or a named tool guarantees a tool call.

API and Agent SDK

stop_reason: "tool_use"Run the tool(s), append the results, continue the loop
stop_reason: "end_turn"Done, so end the loop
Other valuesmax_tokens, stop_sequence, pause_turn, refusal, model_context_window_exceeded
tool_choice: "auto"A tool call or plain text
tool_choice: "any"Must call some tool
{"type":"tool","name":"X"}Must call tool X
SubagentsTask tool, which must be in the coordinator's allowedTools. Context isn't inherited.
PreToolUse hookRuns before the call; can block it or change its input (e.g. block refunds over $500)
PostToolUse hookRuns on the tool's result, before the model sees it, to normalise or transform it. It can't undo the call.

Message Batches API

  • 50% cheaper, up to a 24 h window, no latency guarantee.
  • Up to 100k requests or 256 MB. After 24 h a batch is expired, and expired requests aren't billed. Results are kept 29 days.
  • Results come back unordered, so match them with custom_id. Resubmit only the failed items.
  • No multi-turn tool calling inside one batch request, and no streaming.
  • Use it for overnight or weekly work. Never for a blocking pre-merge check.

Structured output and escalation

  • tool_use plus a JSON schema removes syntax errors, not semantic ones.
  • Retrying with the error message fixes format; it can't create information that isn't there.
  • Several customers match → ask for more identifiers. Never guess.
  • Handoff summary: customer ID, root cause, amount, recommended action.

MCP

  • A failure is signalled with the isError flag, plus errorCategory (transient, validation or permission), isRetryable and a description. Without isRetryable, retries get wasted on errors that will never succeed.
  • A business-rule refusal gets retriable: false (the guide's spelling for this case) and a customer-friendly explanation.
  • A subagent retries transient errors itself and passes up only what it can't fix, with partial results and what it tried.
Transient (timeout, service unavailable)Retry. A subagent recovers locally.
Validation (invalid input)Fix the input, then try again.
Business (policy, e.g. a refund over the limit)No retry. Explain to the customer, or escalate.
Permission (not allowed)No retry. Escalate or ask for access.
  • "No results found" is a valid result, not a failure. A failed search reported as an empty success hides the failure.
  • Project servers go in .mcp.json (committed). Personal ones go in ~/.claude.json. Secrets use ${ENV_VAR}.
  • Mix-ups: the file is ~/.claude.json, not ~/.claude.md. There is no local.mcp.json: local scope also lives in ~/.claude.json, filed under the project.
  • Check a server works: restart, then look in /mcp for it and its tools.
  • All servers' tools are available at once, discovered when they connect.
  • Resources are content catalogues, which cut exploratory calls. Tools are actions.

Built-in tools

  • Grep searches file contents. Glob finds files by path pattern. Glob matches the whole path, not only the name (src/api/**/*.ts), and never looks inside a file.
  • Traps: the question says the files share no naming pattern → Glob is wrong, Grep the contents. The question excludes a folder (e.g. generated files) → a Glob that's too broad is wrong.
  • Edit needs a unique text match. If the anchor isn't unique, use Read then Write.
  • Explore step by step: Grep for entry points, then Read to trace. Don't bulk-read.
